# QW buddy 架构设计（v1 定稿）

本文件是 QW buddy 的架构真相。决策理由见 [`DECISIONS.md`](DECISIONS.md)，独立审核见 [`reviews/2026-09-15-astra-review.md`](reviews/2026-09-15-astra-review.md)。

## 0. 一句话

**装进单个项目的「AI 主控说明书 + 几个脚本」：使用者只提需求，其余（判断、派发、盯、验收、落地、记账）全部自动。**

## 1. 命名与形态

| 项 | 内容 |
|---|---|
| 全称 | `qonnwolf-buddy` |
| 简称 | **QW buddy**（人读场合）／`qwbuddy`（机器场合：目录、命令、文件名） |
| 形态 | **不是独立软件**：一份说明书 + 几个 shell 脚本 + markdown 账本 |
| 母本仓 | `qonnwolfbuddy`——存模板、脚本、安装器 |
| 安装 | 从母本仓执行 `bash bin/qwb-init.sh <项目根>`（复制模板 + 建账本 + 写钩子；幂等）。装好后先在项目的 `qwbuddy/config.sh` 声明本项目自己的质量门，再跑 `qwb-test.sh fast\|full` 验证（未声明门会明确报错，不当成通过） |
| 启动 | 在项目里开 Claude Code / Pi / Codex，说「**你现在是 QW buddy**」→ 读 `qwbuddy/QWBUDDY.md` 变身主控 |

## 2. 三层责任

| 层 | 谁保证它活着 | 状态归谁 | 备注 |
|---|---|---|---|
| **执行层**（工人，跑在 Herdr 窗口里） | **Herdr**：进程常驻，一直跑到成功或失败 | 工人自己往主账本写状态行 | 不需要盯——这是 Herdr 的核心好处 |
| **主控**（AI 会话：Claude Code / Pi / Codex） | **无保证**：会话可能结束、进程可能退出、随时可换人 | **主控无状态**——全部状态在账本；换任何 AI 读账本都能接手 | 唯一的脆弱环节 |
| **运行时**（shell 脚本） | 使用者（无守护进程） | 无状态，只读写账本 | 见到第 4 节 |

## 3. 四大机制

### 3.1 记忆
| 件 | 位置 | 说明 |
|---|---|---|
| 账本 | `<项目根>/tasks/` | 唯一真相。日期命名的任务书 + 结果 + 索引 |
| 错题本 | `<项目根>/tasks/lessons/`（索引 `lessons.md`） | 两级：索引一行 + 详情一文件（现象 / 根因 / 对策） |
| 偏好本 | 主控说明书内 | 使用者偏好与项目约定 |

### 3.2 规矩
- **施工单**：主控把需求写成任务书文件（`tasks/YYYY-MM-DD-<主题>.md`），工人读文件干活。
  **所有任务都经文件派发，无隐性依赖**——换会话、换 AI、重启都不丢。
- **隔离干活**：`qwb-run.sh` 建 Git worktree 并在 Herdr Spaces 登记独立 worktree workspace，代码改动只在副本里。
  **worktree 规范（四步 + 两条补充）**：
  - **开**：`<项目>/.worktrees/<任务id>/`，一任务一个；开之前**先清点**——有已完成任务的残留就先收掉。**默认就开**：`qwb-run.sh` 不给 worktree 参数时**自动创建隔离副本**（与「工人代码一律留在副本」直接对齐）；确实要往项目根派发时必须显式 `--here`，且提示词会写明这是**非隔离**目录。
  - **收·成功**：验收通过 → 合并 / 推送 → 核对并关闭本票空闲 Herdr Space → `git worktree remove` + 按已核实 OID 原子删分支 → 记账。
  - **收·废弃**：先提交到该分支 → 核对并关闭本票空闲 Herdr Space → `git tag archive/<任务id>` → `git worktree remove` + 按已归档 OID 原子删分支 → 记账。
    **为什么**：这样废弃的工作不会丢（一个标签就能找回），也不再占目录和分支——比「一律不许删」更实用。
  - **留·例外**：只允许两种——① 等使用者裁决的；② 有冲突待解的。且必须**点名**（账本一行），不得默默留下。
  - **归属**：谁派生谁收尾——主控收尾它派给工人的 worktree。
  - **补**：`git worktree prune` 清「目录已删但 git 还记着」的元数据残留。
  - **实现**：四步已由 `bin/qwb-worktree.sh` 落地（`list` 列残留 / `finish <任务id> --merged|--archive|--keep`），收尾动作与记账由脚本做，**成功/废弃/例外三选一的判断仍归主控**；`qwb-run.sh --create-worktree` 在开副本前会清点残留并**警告**（不阻塞）。
  - **detached HEAD**：判断与归档一律以 **worktree 当前 HEAD 的实际提交**为准（不是同名分支）。detached 时 `--archive` 的标签指向实际工作、且**不删**指向别处的同名分支；`--merged` 按实际提交是否已合并决定；`git status` 失败视为「状态未知」→ **拒绝**，不得当作干净放行。
  - **收尾期间不得被推进（TOCTOU，已知边界）**：收尾开始时读到的 HEAD 只在「那一刻」有效。`worktree remove` 前复核实际 HEAD；删分支使用带旧 OID 条件的 `update-ref -d`。变了就拒绝删除并保留已打的标签。分支身份读取失败同样拒绝——不猜、不回退成任务 id。
    **边界（明示，不要当成已封死）**：复核与删除是**两次独立 Git 调用**，两者之间仍有窗口；且 detached HEAD 上的新提交**不更新任何 ref**，无法被任何前置检查捕获。因此——**收尾的前提是该副本的写入者已停止**（工人已收工）。若违反此前提，窗口内产生的提交会变成未引用对象，可 `git fsck --lost-found` 找回（不是静默清除）。脚本的成功输出会带上删除依据的完整 OID 与这条限制。
  - **`--keep` 不做脏检查**（它本来就不动 git）：规范明确允许保留「有冲突待解」的 worktree，不能被「工作区不干净」挡住；脏检查只作用于会删东西的 `--merged` / `--archive`。
- **验货门**：**不采信工人自述**。验收由主控独立跑项目自己的检查命令（typecheck / test 等），并把「跑了什么、结果、结论」写进账本留痕——**权力下放 + 可审计**。
- **主控可自干小活**（改动一行这类、无独立验收价值的），同样要留一行「怎么验证的」。

### 3.3 保险

| 保险 | 形态 | 说明 |
|---|---|---|
| **护栏** | **行为约定**（写进任务书与角色文件） | 「不许改白名单外文件」由主控在任务书里写明范围、由执行者遵守；**不做代码强制**（要强制就得给每个项目编一份文件白名单，属重机械） |
| **锁** | **代码**（最小实现） | `bin/qwb-lock.sh`：`mkdir` 原子目录锁 `<项目>/qwbuddy/.controller.lock`。`qwb-run.sh` 派发前抢锁，**他人持锁则拒绝派发**；同一主控（自己就是锁主）可重复派发。不做 `--force` / 超时自动夺锁——残留锁由使用者确认后手动 `release` |

### 3.4 运行时——唤醒主控机制（核心）
见第 4 节。

## 4. 唤醒主控机制

**目的**：主控回合结束就不回来了；需要有人把它叫醒，让它接着验收、派下一步。**全程不打扰使用者。**

### 4.1 形态

```
【主控】常驻一个 Herdr 窗口（Claude Code / Pi / Codex），空闲时不烧 token
【值守】另一个窗口跑 qwb-wake.sh（纯 shell，约 60 行）
【动作】事件或超时 → 检查账本未结项 → 有 → 叫醒主控
```

### 4.2 事件来源（全部 Herdr 原生）

| 等待 | 命令 | 说明 |
|---|---|---|
| 工人完成 | `herdr agent wait <工人窗口>` | 等会话状态变化 |
| 工人写了完成状态行 | `herdr pane wait-output --match "done:"` | 更精确的信号 |
| 兜底 | `--timeout <毫秒>` | **Herdr 超时单位是毫秒**。QW buddy 实际用的等待上限是 `config.sh` 的 `QWB_WAKE_INTERVAL_MS`（默认 `120000` = 2 分钟）——见 §4.3 与 §10 |

### 4.3 以「未结项」为准，而不是一次性通知（审核修正 ②；Astra medium 审核后修订）

值守循环**不能**是「事件发生 → 通知一次」——那样主控忙、投递失败、值守重启都会丢事。正确做法：

```
循环：
  事件 或 超时
  → 读账本，列出「未结项」（state ∈ {running, blocked, needs-decision}）
  → 有未结项且「进展指纹」已变 → 叫醒主控（herdr pane run）
       指纹 fp = sha1(state 值 + 最后一条 working:/done:/blocked:/needs-decision: 行原文)
       叫醒后写 wake: <时间戳> state=<值> fp=<sha1>；指纹未变则不再叫
  → 无未结项 → 继续等
```

- **去重键是「进展指纹」，不是 `state:`**：`state:` 只有主控能改，而工人只追加状态行；只比 `state` 会导致「工人完成后再也不会叫主控」（工人写 `done:` 不改 `state`）。指纹含最后一条状态行，工人一写 `done:` / `blocked:` 指纹即变 → 重新叫醒。
- **时间兜底重叫只对 `running` 生效**：指纹未变**不等于**不用管——工人可能挂起/崩溃而**没追加任何行**（此时指纹永远不变）。所以对 `running` 票还要看**最近一条 `wake:` 行的时间戳**：距现在 ≥ `QWB_REWAKE_MS`（默认 1800000 = 30 分钟，0 关闭）就**即使指纹未变也再叫一次**，把超时判断交回主控。时间戳解析失败时保守处理为「超期 → 叫醒」（宁可多叫，不可漏叫）。`blocked`/`needs-decision` 等的是**主控裁决或使用者**，指纹未变即跳过——对它们重叫只是烧主控 token。
- **工人丢失也是一次进展**：`running` 票判定为工人丢失（最新 `dispatch:` 的 pane 查不到，或 pane 在但无 agent——关机/herdr 重启后工人没了）时，指纹输入追加 `lost=<pane>` 段：工人一消失指纹变一次 → 叫一次，之后指纹不变不重叫。
- **一轮只发一条投递**：值守一轮把所有「要叫」的票拼进**同一条** `herdr pane run` 文本（各票文件名、state、最后状态行截 160 字符、丢失标「工人丢失」）；投递成功才逐票写 `wake:` 行，失败一行都不写（下轮重试），主循环不退出。
- **投递失败不丢事**：`herdr pane run` 失败时**不写** `wake:` 行（保持未叫、下轮重试）、报 stderr、继续处理下一项，主循环**不得退出**。
- **等待**：只对**未结项**任务书取 `dispatch:` 行、用**时间戳最新**的一条做 `herdr agent wait`；**一轮的总耗时预算为约 1×interval——无论等待成功还是失败都把已耗时计入预算**：耗时接近 interval 就直接下一轮（不重复 sleep），耗时远小于 interval（立即成功 / 立即失败）就补 sleep 到预算。补 sleep 按**剩余毫秒换算小数秒**（不取整整秒），使短周期（如 `interval=100`）也满足预算。**不得忙循环，也不得重复等待**。（工人 idle 时 `agent wait` 会**立即成功**，是最容易退化成忙循环的路径。）
- **不需要队列、不需要 ACK 协议、不需要数据库**——账本自己承担这个职责。
- **工人退出 ≠ 完成**：退出但账本里没有结论的，仍算未结项。

### 4.4 两条硬约束（审核修正）

1. `herdr agent wait` 等的是**会话状态**，**不等于验收成功**——**验收必须主控自己跑检查并写结论**，不能据此销账。
2. **叫醒 ≠ 通知使用者**：唯一的动作是 `herdr agent prompt` 到主控窗口。任何「叫醒使用者」的通道（钉钉、系统通知、弹窗）**一律不要**。

## 5. 账本（唯一真相，路径唯一）

**审核修正 ①：账本路径必须唯一，且工人与主控共读同一本。**

| 项 | 规定 |
|---|---|
| 位置 | **`<项目根>/tasks/`**（沿用现有习惯，唯一） |
| 工人 | 派发时给它**主账本的绝对路径**；工人**只往主账本追加自己的结果 / 状态行** |
| 工人的代码改动 | **一律留在隔离副本里**，不写主账本所在目录的代码 |
| 主控 | 维护索引；写验收结论；写「怎么验证的」 |
| 为什么 | 工人在副本里干活，写进副本的 `tasks/` 主控在主目录**看不到**；只有绝对路径写主账本才能保证「工人完成 → 主控看得到」 |

状态行约定（工人写，主控读）：

```
working: <进展>
done: <结果 + 证据（跑了什么检查、结果如何）>
blocked: <卡在哪，需要什么>
needs-decision: <需要判断的选项>
```

**状态行前缀只认列首**——值守指纹、疑点门与 lint 都只把行首的 `working:`/`done:`/… 当状态行。文档/模板里的示例必须**缩进**（见 `TASK.md` §4），否则照模板新建的票会被当成已有状态；列首的占位示例行（`working: … <…>` 带 `<>` 未填占位符）`qwb-lint.sh` 第 8 项会警告。

## 6. 身份切换机制

**角色 = 一份独立说明书文件；切换 = 一句话；产出物标注角色。**

```
qwbuddy/roles/
├── 主控.md     立场：派发与验收；禁止：自己写实现（小活除外）
├── 审核者.md   立场：只挑错、不提方案；禁止：改代码
├── 执行者.md   立场：只干票内的事；禁止：扩大范围、改白名单外文件
├── 咨询师.md   立场：只给判断和建议；禁止：派活、改代码
└── 维护者.md   立场：按主控限定的批次修复已合入内容；继承执行者边界
```

每个角色文件写三样：**立场 / 产出物 / 禁止事项**。

切换方式：说「切到审核者」→ 读该角色文件 → **明确声明当前身份**。

**性质与限制（审核认定）**：
- 身份切换**只是行为约定**，不是权限隔离，也不清空上下文；
- 根级说明书（`QWBUDDY.md`）的固定禁令不允许被角色文件推翻；
- **同一会话换角色 ≠ 独立审核**——所以「审核必须换模型家族」这条硬规矩保留；
- **不单独记切换流水**：产出物与验收记录里标明角色即可。
- 维护者是按需执行者；主控限定基线、范围和预算，协调在途文件并验收独立维护产物。复用现有派发、账本、审核及验证运行时；维护进度不成为无关功能的合并门禁。

## 7. 工人表 + 派工规则

### 7.1 工人（MVP 只支持三家）

| 工人 | 启动 | 能力档 | 擅长 |
|---|---|---|---|
| codex | `codex` | 强实现 | 复杂代码、重构 |
| pi | `pi` | 快速 / 便宜 | 常规执行、机械改动、调研 |
| claude | `claude` | 难活 / 审核 | 架构判断、对抗审查、前端 |

**硬限制：工人一律在 Herdr 窗口里交互式运行，禁用 headless 模式**（使用者要看得见运行情况）。加一个新工人 = 工人表加一行。

### 7.2 派工规则（自然语言，写进 config）

- 复杂架构 / 高风险改动 → 强档（codex / claude）
- 常规实现 / 机械改动 → 快档（pi）
- 审核、挑错 → **必须换一个模型家族**（不能自己审自己）
- 实时信息、联网 → 按能力表挑

### 7.3 额度判定

派工前查一次本机额度（`quota-axi`，覆盖本机已登录渠道）。**模型判定 = 智力档（活需要多聪明）× 额度现状（谁还有余量）**。

额度只是**派发时的参考**，不保证执行一定成功。

## 8. 布局

### 8.1 装进项目后的布局

```
<项目根>/
├── AGENTS.md            ← 加几行钩子（Pi / Codex 进门自动读）
├── CLAUDE.md            ← 加几行钩子（Claude 进门自动读）
├── tasks/               ← 账本（唯一真相）
│   ├── YYYY-MM-DD-<主题>.md     任务书
│   ├── <主题>-result.md         工人结果
│   ├── lessons.md               错题本索引
│   └── lessons/<主题>.md        错题本详情
└── qwbuddy/
    ├── QWBUDDY.md       主控总说明书
    ├── TASK.md          任务书模板（含验收场景块：Given/When/Then + 至少一条失败路径）
    ├── roles/           主控 / 审核者 / 执行者 / 咨询师
    ├── config.sh        工人表 + 派工规则 + 超时 + 快门/全门（bash 可直接 source，唯一来源）
    └── bin/
        ├── qwb-init.sh      **母本仓专用**：装进新项目（幂等；不复制自身到目标项目）
        ├── qwb-run.sh       派发 + 记账（派发前：清点残留 + **验收场景门** + **默认开隔离副本**）
        ├── qwb-wake.sh      值守：以未结项为准叫醒主控（支持假时钟注入便于测试）
        ├── qwb-status.sh    点名 + 汇报
        ├── qwb-lock.sh      主控锁（mkdir 原子目录锁）
        ├── qwb-worktree.sh  worktree 清点与收尾（list / finish）
        ├── qwb-test.sh      快门/全门执行器（跑 config 声明的 QWB_GATE_FAST/FULL）
        └── qwb-lint.sh      自身 lint（承诺未实现 / state 值域 / 死配置 / 非 ASCII 陷阱）
```

**零钩子、零插件、零队列、零数据库、零外部服务。**

**测试纪律（可执行的，不只是写在纸上的）**：先场景后代码——任务书必须有「验收场景」块（Given/When/Then + **至少一条失败路径**），**派发时会硬拦**，并把场景块指纹写入 `scenarios-fp:`，**场景在派发后被改动会被 lint 抓出来**；快门/全门分级（改一行跑快门，合并前跑全门；未声明门会报错而**不当成通过**）；假替身必须有契约基线（`tests/fixtures/` 真录样本 + **真实 JSON 路径校验**）；时间逻辑用可注入时钟而非真 `sleep`；**每道门都必须有负例断言**（在错误输入下必须失败，且固化成测试——前两轮都栽在「门看起来通过、其实没能力失败」）。

### 8.2 母本仓布局

见 [`../README.md`](../README.md)。母本仓不给自己装 qwbuddy/：主控在母本仓内工作时创建的 qwbuddy/（锁、值守、安装副本等运行态）在 `.gitignore` 忽略，配置回退读跟踪的 `qwb.config.sh`；两份配置同时存在时质量门必须一致（qwb-lint.sh 有专项检查）。

## 9. 一次完整流转

```
【使用者】提需求（说一句）
   ↓
【主控】写任务书 tasks/<日期>-<主题>.md
        git worktree add + herdr worktree open（隔离副本在 Spaces 可见）
        herdr tab create + rename（中文标签）
        herdr agent start（工人）
        herdr agent prompt（送任务书 + 主账本绝对路径）
        账本记：任务、窗口、派发时间、状态=running
   ↓
【工人】在 Herdr 窗口里自主跑到成功或失败
        每阶段往主账本追加状态行（worker 只追加，不改别人的行）
   ↓
【值守】herdr agent wait / pane wait-output / 超时
        → 查账本未结项 → 有 → herdr agent prompt 主控窗口 "看账本"
   ↓
【主控】被叫醒 → 读账本
        → 跑验货门（项目自己的检查命令）
        → 写结论 + 证据到账本
        → 通过 → 落地（合并副本分支）；不通过 → 返工或记错题
        → 派下一步；或回空闲
   ↓
【使用者】随时问「怎么样了」→ qwb-status.sh 读账本 + 问 Herdr → 汇报
          （不会被任何通知打扰）
```

## 10. MVP 边界（明确不保证什么）

**边界选择 A（使用者已确认）**：

- ✅ 保证：**存活且空闲的主控**能被唤醒并继续处理账本。
- ❌ 不保证：**主控进程已退出 / 整机重启**后自动恢复。这种情况由**使用者重新启动主控**，主控开局第一件事读账本、从账本续接。
- ❌ 不保证：值守脚本自己长期存活——它由使用者启动（或一条开机命令）。
- ⏱ 已知限制（**并发唤醒延迟**）：值守每轮只对**未结项任务里最新一条** `dispatch:` 的 pane 做**一次** `herdr agent wait`。因此两个工人并行时，另一个工人的完成要等本轮等待结束、循环回头扫账本时才会被发现。**一轮的总耗时预算为约 1×`QWB_WAKE_INTERVAL_MS`（默认 2 分钟）**（等待已耗掉的时间计入预算，不再重复 sleep）。MVP（单项目、人工盯）接受此延迟，不为它改架构。
- 说明：不做「自动拉起主控」，因为那需要守护进程 + 会话恢复，属于重机械，与 MVP 冲突。
- 👁 **重启后工人丢失可见**：主控重启后的开局点名用 `qwb-status.sh`——`running` 票下若标「工人丢失: pane <id> 已不存在/无 agent」（判定：最新 `dispatch:` 的 pane 查 `herdr pane get` 返回 `pane_not_found`，或 pane 在但 agent 字段为空；查询失败显示「工人状态未知」，不当丢失），说明工人已不在、账本没有结论。处置：**重派同一票**——worktree 创建幂等，续接不另开副本。值守同样把丢失算一次进展（指纹含 `lost=<pane>` 段，叫一次即止）。

## 11. 明确不做

| 不做 | 原因 |
|---|---|
| 项目注册表、克隆同步、上游同步 | 单项目不需要——它自己就是项目 |
| 多机 secondmate | 单机单项目 |
| 常驻哨兵 / cron / 定时轮询 | 单人项目无场景（Herdr 事件替代轮询） |
| 对外通道（公开应答 / 语音 / 链路追踪） | 不要 |
| 自更新、子代理副意识、各家产品钩子插件 | 运行时搬出 AI 后不需要 |
| **任何通知使用者的通道** | 使用者睡觉不想被打扰 |
| 唤醒队列 + ACK 协议 + 数据库 | 账本承担该职责 |
| no-mistakes 全流水线 | 改用项目自己的检查命令 |
| 其他终端后端（tmux / zellij / orca / cmux） | 只用 Herdr |
| 角色切换流水账 | 产出物标角色即可（审核建议砍） |

## 12. 两条判断尺子

1. **谁的状态**：状态属于**产品**（会话 / 模型 / 厂商）→ 交给那个产品；属于**使用者和项目**（任务 / 验收 / 教训）→ 放在产品外面，也就是 QW buddy 这层。
2. **薄即抗淘汰**：Harness（Claude Code / Codex / Pi）会越来越强，会吃掉「等待、通知、记忆」这类事；QW buddy 只持有它吃不掉的东西——**跨厂商调度 + 属于项目的账本与验收纪律**。
