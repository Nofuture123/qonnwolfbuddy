## 审点 3：质量 / 速度 / token

**质量（强项）**：453 条 smoke + 每门负例 + 反转验证 + 场景冻结指纹 + 疑点门 + 审核换家族可核验。母本仓自身 33 张票、9 条错题，返修率高但都留痕。判定：质量机制已足够，不需要再加门。

**速度**：值守 2 min 轮询 + agent wait 事件，机器侧不是瓶颈。瓶颈全在「要人按」：信任框（1-1）、锁残留（2-2）、merge 授权（本仓惯例）、可见值守窗（1-5）。修 1-1/2-2 后，从「提需求」到「verified」中间可以零人工。

**token（弱项）**：主控是唯一烧 token 的角色，浪费点按大小：
1. 值守本身：可见 tab 模式下不烧 token，但每次唤醒 = 一个主控回合；隐形化（Stop hook）后值守零 token、唤醒才起回合——最大项，已开票。
2. 逐项唤醒（2-3）+ REWAKE 无差别重叫（2-4）：一张等使用者的 needs-decision 票挂 8 小时 = 16 个空回合。
3. 唤醒文本「读 tasks/」+ 开局点名「读每份头部」：生产项目 282 份 → 应改为 `qwb-status.sh` + 只读点名的票（`audit-install-fixes` §D）。
4. 工人侧：提示词短、票自带附页，合理；worktree 无依赖（1-2）会让工人多花回合摸索。

判定：**未真正平衡**——质量侧到位，token 侧四处可修、都不动架构。修完后平衡。
