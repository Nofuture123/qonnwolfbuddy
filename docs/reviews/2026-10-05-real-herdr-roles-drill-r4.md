## 本轮发现

演练主控的笔记、时间线、各窗口记录、两张票终态在 `.qwb-tmp/drill-roles-r4/`（`notes.md`、`timeline.log`、`evidence/`）。标「主控已核对代码」的是本仓主控读过对应代码，其余是演练主控的记录。

- **U1 审核工人收工不回票，全员空等（缺陷）。** 主控已核对代码：`bin/qwb-run.sh` 发给审核工人的提示词里没有「把结论写进票」的要求（发给实现工人的有）；值守对在途工人只有「窗口消失立刻叫」和「满 `QWB_REWAKE_MS`（默认 30 分钟）无新事件才叫」两路，「已收工、票上没交代」也要等满 30 分钟。第三轮审核工人自己写了 `done:`，所以没暴露。已开票 `worker-silent-end`。
- **U2 修订撞上已派出的工人，说明书没覆盖。** 副主控开票后 39 秒就派了工，修订到达时工人已在写 V1。说明书的修订分支只写了「开票后、派工前」与「门控验收阶段」两种时机。演练主控的处理（V1 的 `done:` 不送门控、按 not-applied 办结，等修订、重新授权、重做后的 V2）走通了，但全靠它自己判断。
- **U3 修订后系统给主控留了一条要手工办结的阻塞。** `revise` 之后票上自动出现 `blocked: planner-not-ready … 首次启动无明确实施授权/预算` 并交给主控；主控 `plan-authorize` 之后它仍挂着，要走四步办结。说明书没提。
- **U4 重派复用了原工人的同一个会话。** 说明书只说「沿同票及既有副本派工」；实际是同一个窗口、同一个 Pi 进程、同一份会话记录承载 V1 与 V2 两轮，取证时要知道这一点。
- **U5 字段含义没说明。** 修订请求在 `pending` 里显示收件人是主控，实际门铃发给了副主控。
- **U6 落地之后 `pending` 仍列出已满足的通知。** 说明书写「成功的 `land-authorize` 已满足匹配的通过与交还通知」，但落地后 `qwb-send.sh pending` 仍列出通过、交还、审核工人活动三条。演练主控不放心，用新操作号逐条办结了。普通进度行同样长期挂在 `pending` 里，是否必须办没写。
- **U7 自检把必填配置判成死配置（缺陷，主控已核对代码）。** 项目里按说明书配置 `QWB_ROLE_PI_CONTROL="verified"` 后，`qwb-lint.sh` 报 `死配置（bin/ 无引用）: QWB_ROLE_PI_CONTROL`、整体 FAIL。原因：`bin/qwb-lint.sh` 第 4 节只把脚本里以 `$` 读取的变量算作被引用，而 `bin/qwb-role.sh` 是把它导出后在内嵌 Python 里读的。模板 `config.sh` 里也没有这一项。
- **U8 说明书自相矛盾。** 常驻流程的前提要求全门真正检查场景，同时又说不要为运行示例改门；演练项目的门是空命令，收据耗时 0 秒也被接受。
- **U9 `.roles/.prompts/` 下指令文件什么时候能回收没写清**（常驻职责不退出时，谁算「相关读者」）。
- 演练主控自报越界：读了清单外的 `qwbuddy/config.sh`、`.claude/settings.json`、`.gitignore`（都不是脚本源码）。
