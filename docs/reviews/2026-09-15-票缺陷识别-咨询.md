## 1. 最终形态与落点

在 `templates/TASK.md` §4、`templates/QWBUDDY.md` §3/§5，以及 `bin/qwb-run.sh` 的派发提示中约定两种追加行：

```text
blocked: spec-defect: <票条款；反例或证据路径；继续照做会错在哪里>
working: spec-resolved: <impl|spec>；<逐项回应及证据；改票位置或保留原票的理由>
```

第一行由工人或主控提出；第二行仅由主控写。一个处置结论覆盖其之前全部未决疑点，不能只回应最后一条；无法裁决就保留未决。普通 `working:`、`done:`、`dispatch:` 均不能解除疑点，新疑点会重新拦截。这里只增加日志约定，不增加头部状态、工人改写权限或每票必填字段。

- **`bin/qwb-run.sh`**：顺序扫描这两类精确前缀，最后一个相关事件为疑点则拒绝实现派发；在创建 worktree、窗口及改票之前检查。报错指向疑点，要求主控处置，不要求必开审核窗口。
- **`bin/qwb-status.sh`**：用同一判定规则额外显示“规格疑点未处理”，不依赖最后一条普通状态行。`templates/QWBUDDY.md` §1 要求接手时先处理这些票。
- **`bin/qwb-wake.sh`**：沿用现有 `blocked:` 唤醒。无需新增顶层 `spec-defect:` 状态及多处识别分支。

该门约束规定的派发入口。直接在已有窗口继续派实现仍依赖主控守约；本轮不扩成 Herdr 通信拦截器。审票复用现有可见 Herdr 审核路径，不经过当前只派“执行者”的 `qwb-run.sh`，因此不会被实现派发门锁死。

## 2. 触发条件：证据优先，重复失败作提醒

**不采用 `rework-count ≥ 2` 自动开审票。** 两次分别修拼写和边界错误，没有理由购买一次独立审票。

| 情况 | 动作 |
|---|---|
| 首次就出现条款冲突、按票实现仍违背上游目标，或验收不能区分对错的具体证据 | 立即记疑点；主控在本次验收中判断，不等第三遍。 |
| 同一验收现象在一次针对性修复后再次失败，且原根因解释无法说明复发 | 主控先核对票和验收；不能用实现证据解释时记疑点。不同问题不累计。 |
| 反例明确且修订仍在授权范围内 | 主控改票、补反例、留处置结论，直接继续原工作；无需另起审票轮次。 |
| 主控与工人对条款解释有实质分歧、缺少可验证反例，或同一疑点被驳回后有新证据复发 | 升级一次独立审票；交付相关条款、反例及直接关联证据，不重读全仓。 |

第二行是验收纪律，**当前不做自动“同一问题”识别**。规范写入 `templates/QWBUDDY.md` §5；独立审票在现有审核角色说明中增加三个审点：① 票内部及上游承诺是否一致；② 场景是否覆盖这次反例和失败路径；③ 验收门能否对已知错误实际失败。结束条件是疑点已有可执行裁决，不顺带开启全项目新一轮审核。

## 3. 归类：判断“需要改哪里”，不统计责任

用 **`impl` / `spec` 两类处置结论**足够：保持任务要求即可纠正的归 `impl`；必须修改任务要求、上游约定或验收定义的归 `spec`。尚不清楚就不写 `spec-resolved:`，无需第三类计数。

例如，票已经明确要求负例能失败，工人却写了恒真断言，是 `impl`；票把“出现负例关键词”当成充分验收标准，是 `spec`。`doc` 和 `gate` 是出错位置，不能单独说明根因；一件事两边都有错时可在同一行写明两项修复，只要需要改规格就归 `spec`。

主控手工判断可接受，也必须允许它被证据推翻。机器适合查未决记录、字段格式与指纹；无法凭一个标签证明归类正确。无需每条返修项归类，只在规格疑点处置时写一次。

## 4. 更薄的做法与修订通道

**零脚本方案确实存在**：只规定 `blocked: spec-defect:` 和主控回应，利用现有唤醒、接手读账本及改票入口。它最便宜，但主控忽略一行文字仍能继续派发，无法可靠纠正本次提出的循环。因此我建议多付一个派发门和一条状态提示的成本。

抽查发现，当前 `bin/qwb-run.sh:117` 已提示“主控确认后删旧指纹，再用 `--accept-new-scenarios` 重建”。因此现状有手动逃生口，但缺少完整的修订记录；不能说完全无法改票。

建议将**正常修订**落在 `bin/qwb-run.sh --revise-scenarios=<原因>`：

1. 主控先停止受影响实现，在票内保留相关旧条款与修改理由，修改场景并完成疑点处置。涉及产品目标改变时沿用已有授权边界，机制本身不扩大改需求权。
2. 参数原因非空、旧指纹存在、场景结构合法才允许修订；在取得主控锁后、任何派发副作用前重新核对并更新，追加 `working: scenarios-revised: old=<fp> new=<fp> reason=<原因与条款记录位置>`。已有的缺基线恢复参数继续只处理缺基线情况。
3. 修订记录与新指纹均成功写入才继续派发；任一步失败就退出。处置结论本身不授权绕过指纹检查。
4. `bin/qwb-lint.sh` 继续核对当前场景指纹；对带修订记录的票，再查最新记录的新指纹等于当前基线。无修订参数的场景差异仍失败。

相关说明落在 `templates/QWBUDDY.md` §6。指纹只能证明文本一致，旧条款与理由才让人看得懂为什么改。共享可写账本不能防恶意伪造，这里不建设身份签名、事务日志或版本数据库。

**失效边界**：所有参与者都没意识到规格可疑时，该方案不会自动发现；修订理由也可能判断错误。它消除“疑点已提出却照旧重派”的机械失误，不承诺自动诊断所有坏票。若后续确实反复漏掉无人提出的规格错误，再考虑返修事件计数；现有材料不足以证明必须现在做。

## 5. 反向风险与限度

- **工人甩锅**：疑点须给条款、反例和影响，标签本身不构成免责或验收失败结论。主控可用证据驳回；不因一句“规格有问题”自动购买独立审核。
- **主控轻率驳回**：处置必须逐项回答，不接受“已看，继续”。同一疑点带新证据复发时升级独立审票；原样重复引用已有回应，避免无限重开。
- **小修拖成两轮**：暂停受影响工作，可继续无争议部分；优先在当前验收中裁决。只拦该票后续实现派发，不冻结其他票。
- **改票迎合实现**：修改依据必须来自上游目标或具体反例，保留旧要求；对已知错误证明相关门会失败，再对修复验证通过。新指纹不等于验收通过。

确认的规格错误，只有能提炼出可复用开票规则时才写入现有 `tasks/lessons/`，正文引用本票即可。不建专项索引，不把每次措辞调整写成教训。

## 6. 成本效率与最小验证

以下为 **[估计]，不是实测**；任务书未给总票数，三次事件不能据此算缺陷率。

| 成本项 | 建议预算 |
|---|---|
| 脚本改动 | `run` 约 35–55 行，`status` 约 5–10 行，`lint` 约 5–15 行，合计约 **45–80 行**；测试与说明另计。机制更少，不保证代码必少于初案。 |
| 普通票 | 无新增必填字段、无独立调用；验收多问一句“按票全做对，目标仍会失败吗”。精简规范进入上下文约增加 200–500 token。 |
| 提出并就地解决疑点 | 一条证据记录、一条回应，约新增 200–600 token；改场景再加一条修订记录，不另写长报告。 |
| 独立审票 | 一次有边界的调用，相关输入与输出合计可按 2k–6k token 粗估；工具读取、推理 token 另计，不据此承诺费用。 |
| 触发频率 | 仅作规划直觉：每 10 票约 1–2 票需要就地核对，其中 0–1 票升级独立审票；当前项目可能更高，不能当实测指标。 |

这笔投入值得，因为普通票不负担计数、分类与固定审票轮次，异常票保留跨主控可读且会影响派发的记录。若原有审核已在进行，加入对应疑点即可，避免重复开窗口。

实现后只补三组有行为区分的验证：① 未决疑点确实阻止派发且无窗口/worktree 副作用，普通 `done:` 不解除、有效处置能解除、后续新疑点重新拦截；② 状态汇总能显示被后续普通日志遮住的疑点，现有唤醒能接收该 `blocked:` 行；③ 无痕改场景失败、显式修订保留旧新指纹并可通过 lint，空原因或写入失败均不得派发。无需为标签分类编写“语义判断测试”。
