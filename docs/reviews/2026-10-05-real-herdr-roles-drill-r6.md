## 故障注入（主仓主控操作，演练主控不知情）

目的：让一个实现工人「正常结束回合但不回票」，看值守多久叫醒谁。三次尝试：

1. **打断式注入（第二个小需求）**：实现工人开工 6 秒后按一次 `esc`，再发一条「只回复收到」的提示。工人照做收工。结果：一分钟门铃没有触发。原因是另一个缺陷（W1），不是新功能的问题。
2. **打偏的一次**：主仓主控同时在同一个隔离会话里开了一个探测窗口，注入脚本把它当成了演练工人。属主仓主控失误，已记入 `fault.log`，探测窗口已关闭。
3. **插话式注入（第三个小需求）**：不打断，在实现工人干活时直接发「只回复收到」。工人在当前步骤后读到这条插话，回复「收到」后收工，会话末条记录时间 11:28:24.754Z，没有写任何状态行。**值守在 11:29:29Z 给票写下门铃记录并叫醒副主控，间隔约 64 秒**（配置的阈值是 60 秒）。

## 本轮发现

演练主控的笔记、时间线、注入记录、各窗口记录在 `.qwb-tmp/drill-roles-r6/`（`notes.md`、`timeline.log`、`fault.log`、`evidence/`）。标「主控已实测」的是本仓主控对着现场或代码核实过的。

- **W1 Pi 工人被打断后，活动判定永远报忙（缺陷，主控已实测）。** 模型正在输出、工具调用还没开始执行时按 `esc`，Pi 写下一条 `stopReason` 为 `aborted` 的助手消息，里面带的工具调用之后不会有对应结果；`bin/qwb-herdr.sh` 的活动判定把它一直算作未完成。此后即使工人又正常答完一轮，仍报 `busy`，一分钟门铃不触发，续派与依赖空闲判定的收尾也会受影响。对照实测：工具已经在执行时按 `esc`，Pi 会补一条出错的工具结果再以 `error` 结束，调用是配对的，判定正常。两份脱敏样本在 `.qwb-tmp/real-herdr-samples/pi-session-aborted-tool-then-clean-turn.jsonl` 与 `pi-session-aborted-during-tool-run.jsonl`。已开票 `pi-aborted-tool-activity`。
- **W2 收到「工人已收工但没有报告」之后，派工者没有可照做的步骤（缺口，主控已实测）。** 门铃文字只说「请读它的窗口或让它补写状态行」。副主控的判断是：在工人窗口里另发提示等于绕开派工脚本另派一次工；启动预算已用完不能重派；这条门铃不是待办交接，没有可标记已处理的东西。于是它只在自己窗口里说明情况。没有任何东西把这件事送到主控。已把口径追加进 `roles-r5-docs`：做完没回票的，派工者可以在工人窗口发一条只要求补写状态行的单行提示，不算新派工；没做完或情况不明的，必须经正式渠道上报主控。**代码层面的兜底（派工者被提醒后若干分钟仍未处理就升级到主控）尚未做**，待 `worker-silent-end` 落地后另开票。
- **W3 说明书与实际不符（演练主控记录，主控已核对第一条）**：`templates/workers.sh` 第 8 行注释仍写「Claude Code role控制未验证，明确拒绝」（演练主控记成了 `config.sh`）；门命令配成 `true` 这种空门时自检不报错，说明书只承诺留空才报错。
- **W4 说明书缺口（演练主控记录）**：新开的票在派工前状态是 `blocked`；职责状态输出里顶层活动为 `idle` 而证据里为 `unknown` 可以并存；副主控开票后主控被叫醒时哪些交接要办；办理函数依赖 `qwb-lib.sh` 里的内部函数却没有说明；演示项目的门默认是空门而说明书要求门要真检查场景；门控的通过与交还通知可能在同一次叫醒里到达。前四条与最后一条已追加进 `roles-r5-docs`。
- **正面结果**：第五轮的三次人工介入全部消失。审核工人的提示词改动生效，结论直接写进了票。门控面对空门没有把退出码 0 当证据，另做了字节检查；主控也独立复核了字节。
