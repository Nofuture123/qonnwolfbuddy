## 二、送审的设计快照（当时版本，已被 DESIGN.md 取代）

> 以下为送审原文。**注意**：其中的 `tasks/` 与 `qwbuddy/tasks/` 路径混用、以及「运行时只有两个脚本」的说法，正是本次审核找出的问题；当前定稿已修正。

```markdown
# QW buddy（qonnwolf-buddy）架构设计 —— 待审核

## 0. 背景与目标
- 使用者：单人开发者，单机，多个独立项目。
- 现状痛点：在项目里用 Claude Code / Codex / Pi 当主控，用 tasks/ 目录（markdown 任务书）派活给工人 agent。三个问题：
  1. 身份切换：CLAUDE.md / AGENTS.md 无法让同一会话在「主控 / 审核者 / 执行者 / 咨询师」之间切换。
  2. 执行模型差异：工人有不同 CLI、不同模型、不同额度和能力。
  3. 缺任务分配标准：什么活发给哪个模型没有明确判据。
- 另发现：主控会「叫不醒」——即使最强模型作主控，任务派完/工人干完后，主控回合结束就不再回来处理，结果没人验收、流程断掉。这是他最想要 firstmate 的机制。
- 目标：极简的、装进单个项目的「主控说明书 + 几个脚本」。明确要求 MVP，禁止过度设计。

## 1. 形态
- 不是独立软件：说明书 + 几个 shell 脚本 + markdown 账本，装进项目目录。
- 启动：项目里开 Claude Code / Pi / Codex，说「你现在是 QW buddy」→ 读 qwbuddy/QWBUDDY.md 变身主控。
- 仓库 qonnwolfbuddy 存母本；用 qwbuddy init 装进新项目。

## 2. 角色分工（三层）
| 层 | 谁保证它活着 | 状态归谁 |
|---|---|---|
| 执行层（工人，跑在 Herdr 窗口） | Herdr 常驻，一直跑到成功或失败 | 工人自己写状态行到账本 |
| 主控（AI 会话） | 无保证，随时可能死/换人 | 账本 |
| 运行时（shell 脚本） | 使用者 | 无状态，只读写账本 |

使用者只做一件事：提需求。验收、落地、超时判断全部下放给主控。

## 3. 四大机制
3.1 记忆：账本 tasks/、错题本 lessons/、偏好本
3.2 规矩：施工单（任务书文件派发）、隔离干活（herdr worktree create）、验货门（不采信工人自述，主控独立跑检查并留痕）、主控可自干小活
3.3 保险：护栏（白名单）、锁
3.4 运行时：唤醒主控机制 —— 主控常驻 Herdr 窗口（空闲不烧 token）；另一个窗口跑值守脚本（约 60 行），用 herdr agent wait / pane wait-output / --timeout 30m 盯事件，事件发生 → herdr agent prompt <主控窗口> "看账本"。零通知人类。卡死判断归主控。不需要唤醒队列、ACK、钩子、daemon、数据库。

## 4. 身份切换机制
roles/{主控,审核者,执行者,咨询师}.md，每个写立场/产出物/禁止事项；一句话切换；切换留痕。

## 5. 工人表 + 派工规则
工人表（启动命令、能力档、擅长）；派工规则（自然语言，仿 crew-dispatch.json）；额度判定（quota-axi，智力档 × 额度现状）。

## 6. 文件清单
项目根 AGENTS.md / CLAUDE.md 钩子 + qwbuddy/{QWBUDDY.md, roles/, config.json, tasks/, lessons/, bin/{qwb-init,qwb-run,qwb-wake,qwb-status}.sh}；约 4 个脚本 300 行；零钩子、零插件、零队列、零数据库、零外部服务。

## 7. 明确砍掉
项目注册表、克隆同步、上游同步、多机 secondmate、常驻哨兵/cron、对外通道、自更新、子代理副意识、各家产品钩子插件、通知人类的任何通道、唤醒队列+ACK、no-mistakes 全流水线、其他终端后端。

## 8. 请审核的三点（严格限于这三点）
1. 有没有会「丢事 / 流程断掉 / 系统跑不起来」的机制缺失？（只列真正致命的）
2. 有没有明显多余、应该砍掉的过度设计？
3. 身份切换 / 派工路由 / 唤醒主控 三个机制的最小实现里，有没有哪个在原理上不成立？
要求：MVP 优先，明确区分「必须补」与「可以不要」，不要提出新的功能需求。
```

## 三、审核结论（原文要点）

### (1) 必须补 —— 否则会丢事或断流程

**1. 工人与主控必须读写同一本账本。**
工人在 worktree 中执行，如果结果写进副本里的 `tasks/`，主控原目录不会自动看到；送审正文还混用了 `tasks/` 和 `qwbuddy/tasks/`。
*最小补法*：确定唯一账本路径，派发时给工人绝对路径；工人只更新自己的任务结果，共享索引由主控维护。

**2. 唤醒不能是一次性通知，必须以「尚未处理的任务」为准。**
当前没有说明：主控忙时提示未被处理、提示发送失败、值守重启后谁再来接这件事。仅有工人完成事件，不代表验收已经发生。
*最小补法*：启动和超时后重新检查账本中的未结任务；未验收就仍是待办，直到主控写入处理结果。工人退出但没有结果，也不能直接当作完成。不需要另建队列或 ACK 协议。

**3. 必须解决「主控可以死，但使用者只提需求」的矛盾。**
Herdr 窗口还在，不等于里面的 AI 进程还在；向已退出的主控发送提示，不能恢复主控。必须二选一：
- 接受 MVP 边界：只保证活着的空闲主控能被唤醒；进程退出或整机重启后由使用者重新启动，再从账本续接；
- 或保留无人接管承诺：值守必须能恢复主控进程。
不必做守护进程体系，但不能同时声称「允许主控死亡、无人恢复、流程仍能自动继续」。

### (2) 可以不要 —— 过度设计

- **独立的唤醒队列、ACK、数据库、各家插件：继续不做。** 上述补缺不依赖它们。
- **角色切换每次单独记账：可以砍。** 任务产出和验收记录标明角色即可，无须维护身份切换流水。
- 其余没有明显必须砍的部分。四份角色说明、工人表、简单派工规则本身不算过度设计。**不要为了「极简」砍掉账本或独立验收。**

### (3) 三个最小机制是否在原理上成立

| 机制 | 判断 |
|---|---|
| 身份切换 | **成立，但只是行为约定**，不是权限隔离或上下文清空。根级说明必须允许切换，角色文件不能推翻上层固定禁令；**同一会话换角色不等于换模型独立审核**。 |
| 派工路由 | **成立。** 自然语言规则 + 工人启动命令 + 额度查询，足够支撑主控选人。额度是派发时的参考，不是执行成功保证。 |
| 唤醒主控 | **对存活且可接收输入的会话成立；对已经死亡的会话不成立。** 补上 (1) 中的待办重查与恢复边界即可，不需要另造调度系统。 |

### (4) 直接影响脚本运行的细节

- 本机 Herdr 帮助标注**超时单位为毫秒**，设计中的 `--timeout 30m` 应改为 `--timeout 1800000`。
- `herdr agent wait` 等的是**会话状态**，不是任务验收成功，**不能直接据此销账**。
