## 审点 1：G1 致命项

### U1 — 致命：保存的 OID 与删除时的实际工作仍可错位

位置：`bin/qwb-worktree.sh:101-102`、`:115-124`、`:133-147`、`:157-166`；违反 `docs/DESIGN.md:47`、`:52` 的归档可找回与实际提交要求。

最小交错场景：

1. 同名分支 t 停在 A；worktree detached 于 B。脚本读取 B，status 干净。
2. `--archive` 创建 `archive/t → B`。
3. 工人或另一 Git 进程在该 detached worktree 提交 C，工作区再次干净。
4. 脚本继续 `worktree remove`，删除实际位于 C 的 worktree，仍报告归档成功。标签只能找回 B，C 没有被本次归档保存。无需未提交文件，也无需 `--force`。

内存验证直接执行原文件第 100–173 行，Git 替身返回 detached/B/干净，在 remove 调用处模拟上述已完成的并发提交。原始记录：

```text
concurrent_commit exit=0
TAG B
REMOVE actual_HEAD=C
已归档：tag archive/t → detached HEAD B；worktree 已删；保留分支 t（它不指向本工作区）
```

这证明脚本控制流不检测交错；真实 Git 并发删除未执行。相同窗口也存在于 `--merged`：已合并 B 通过判断后，detached HEAD 新增未合并 C，删除前不再核对。attached 情况在打标签后新增 C，随后的 `branch -D` 也不校验标签是否覆盖分支当前提交。

同一审点的失败注入还显示：第 101 行读取分支名失败会被 `|| true` 吞掉，第 106–107 行回退为任务 id，继续归档后 `branch -D t`；输出为 `branch_read_failure exit=0 / TAG B / DELETE_BRANCH t`。此时实际分支身份未知，仍可能删除指向别处的同名分支。该注入仅证明失败处理路径，未声称已在真实 Git 制造该瞬时失败。
