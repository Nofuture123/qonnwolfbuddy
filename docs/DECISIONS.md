# QW buddy 决策记录

本文件记录每条设计结论、其理由，以及被否掉的替代方案。架构本体见 [`DESIGN.md`](DESIGN.md)，独立审核见 [`reviews/2026-09-15-astra-review.md`](reviews/2026-09-15-astra-review.md)。

记录日期：2026-09-14 ~ 09-15，与使用者逐步定案。

---

## 一、命名

**结论**：全称 `qonnwolf-buddy`（Q-Wolf Buddy），简称 **QW buddy**；机器场合（目录 / 命令 / 文件名）一律 `qwbuddy`。

**理由**：仓库名、命令行不接受大写与空格；人读场合需要可读的写法。二者是同一个名字的两种场合写法。

**否掉的**：`QW Mate`（早期误记，已废弃）；纯航海名（skipper / dinghy / coxswain 等，与品牌无关且 npm 多被占用）。

## 二、形态：装进项目，不是独立程序

**结论**：QW buddy = 一份说明书 + 几个 shell 脚本 + markdown 账本，**装进单个项目**；启动方式是在项目里开 Claude Code / Pi / Codex 并说「你现在是 QW buddy」。

**理由**：
- 使用者的真实场景是「在某个具体项目里干活」，不是「管一支船队」；
- 说明书由产品自身在会话开始时自动加载（`AGENTS.md` / `CLAUDE.md`），所以「变身」不需要任何额外程序；
- 单项目 = 天然轻：不需要注册表、不需要跨项目管理。

**否掉的**：
- **独立文件夹 + 管多个项目**（firstmate 形态）——使用者明确指出「太重」，且他不想要跨项目管理；
- **编译出来的独立软件**——多余；说明书 + 脚本已经能表达全部机制。

## 三、四大类机制

**结论**：记忆 / 规矩 / 保险 / 运行时。

**理由**：
- 使用者起初把「状态机」列为独立机制，后自行归入**记忆**——状态机本质是「跨会话记住活到哪了」；
- 对照 firstmate 的实体文件逐组盘点后，**唤醒机制不属于前四类中的任何一类**（它不是记忆、不是规矩、不是保险），它是让循环转起来的机器，因此单列「**运行时**」；
- 这一分类的意义在于**砍**：单项目下「运行时」是唯一能大幅瘦身的一类。

## 四、运行时：焦点是主控，不是执行层

**结论**：**运行时盯主控，不盯执行层。**

**理由**（使用者洞察）：
- 工人跑在 Herdr 窗口里，**Herdr 保证它一直跑到成功或失败**——派发与回读都不会卡；
- 唯一会「卡死」的情况是**主控没去看任务完成情况**——主控回合结束后不再回来；
- 所以运行时的职责是「让主控不必记得去看 / 忘了也能被叫回来」。

**否掉的**：把运行时做成 firstmate 那样的「盯工人」系统（巡检各窗口、判定 stale、唤醒队列、ACK 协议）——那是 2.4 万行的来源，且盯错了对象。

## 五、运行时演进（三次，含一次纠错）

| 阶段 | 结论 | 理由 |
|---|---|---|
| ① | 前台等待（主控阻塞等工人跑完） | 最省机器；**但被否**：工人要跑在 headless 模式才能同步等，而使用者要求看得见 |
| ② | Herdr 窗口 + 事件驱动（`herdr agent wait` / `pane wait-output`） | 用 Herdr 的**阻塞等待**替代轮询：不空转、不耗算力、不需要给每家产品写钩子 |
| ③ | **值守脚本必须存在**——它的唯一动作是**叫醒主控** | ②曾被我一路砍到「两个脚本、零值守」，**这是砍错了**：使用者的头号需求就是 firstmate 的**主控唤醒机制**（连最强模型作主控也会「叫不醒」）。修正：值守回来，但只叫醒主控 |

## 六、「叫醒主控」≠「通知使用者」

**结论**：**零通知使用者**；**必须有叫醒主控**。

**理由**：两者被我早期混为一谈。使用者明确：睡觉时不想被任何东西打扰（钉钉、系统通知一律不要）；但他需要主控自己回来干活。所以：

| 动作 | 是否保留 |
|---|---|
| 叫醒使用者（钉钉 / 通知 / 弹窗） | ❌ 全部砍掉 |
| 叫醒主控（`herdr agent prompt <主控窗口>`） | ✅ 保留，是运行时核心 |

**否掉的**：钉钉通道（使用者明确否决，且其场景是「睡觉不被打扰」）；`herdr notification` 等一切面向人的推送。

## 七、验收权下放给主控

**结论**：**使用者只提需求**；哪些需要审核、哪些不需要、验收通过后怎么落地，全部由主控判断与执行。

**理由**（使用者原话）：他不是唯一的验收人；他选推理能力强、知识面广的模型作主控，因为它对程序的理解比他强；连超时/卡死也归主控判断。

**必带的保险**：**验收必须留证据**——主控把「跑了什么检查、结果、结论」写进账本（含主控自干的小活）。可能永远没人看，但必须留，使权力下放**可审计**。

**否掉的**：把使用者当唯一验收人（我最初的错误假设，已被使用者纠正）。

## 八、不设常驻岗位，动态组队

**结论**：默认**一个全栈工人包干**；大活按**模块**拆并行（不按前端/后端拆）；每次交付配**独立验收 agent**（唯一值得专职的角色）；架构按需**临时**评审 agent，审完即散；CI/CD 交**脚本**。不设常驻架构师 / 前端 / 后端。

**理由**：
- AI 没有「手艺生疏」问题，都能写全栈；按技术栈拆会让一次跨层改动被割裂成两半、通过文件传话，最容易丢信息；
- 人类团队的分法是按**职位**分；AI 该按**改动边界**与**职责性质**分；
- 唯一真实的对抗关系是「写实现的人 vs 挑错的人」——所以独立验收 agent 值得专职，这也正是 firstmate 独立审查的原理。

**否掉的**：照搬人类团队结构（架构师 / 前端 / 后端 / 测试 / CI-CD 五个常驻角色）——会产生空转岗位与上下文割裂；CI/CD 本来就不需要 AI。

## 九、身份切换

**结论**：角色 = 独立说明书文件（`roles/` 四份）；切换 = 一句话；产出物标注角色。

**性质限制**（审核认定）：
- 只是**行为约定**，不是权限隔离，也不清空上下文；
- 根级说明书的固定禁令**不可被角色文件推翻**；
- **同一会话换角色 ≠ 独立审核** → 「审核必须换模型家族」保留为硬规矩。

**否掉的**：每次切换单独记流水账——产出物标角色即可（审核建议，采纳）。

## 十、工人与主控的产品选择

**结论**：
- **工人**：Codex / Pi / Claude Code 三家；**一律在 Herdr 窗口里交互式运行**；**禁用 headless**。
- **主控**：首选 Claude Code；说明书**产品中立**，Pi / Codex 也能当主控，零新代码。
- **不用**：Cursor、Kimi、Rovo 等。

**理由**：
- 使用者要求「看得见子任务运行情况」——这是 Herdr 带给他的确定好处；
- 产品中立让主控**可以随时换人**，因为状态在账本里而不在模型脑子里；
- 三家之外的产品没有实际使用场景，支持它们只会复制 firstmate 的「每家一根线」问题。

**否掉的**：headless 工人（使用者明确否决）；「每家产品写一套钩子 / 插件」（运行时搬出 AI 后不再需要）。

## 十一、Harness 边界（为什么这东西不会被淘汰）

**结论**：两条尺子——

1. **谁的状态**：状态属于**产品**（会话 / 模型 / 厂商）→ 交给产品；属于**使用者与项目**（任务 / 验收 / 教训）→ 放在产品外面（我们这层）。
2. **薄即抗淘汰**：Harness 会越来越强，吃掉「等待、通知、记忆」；QW buddy 只持有它吃不掉的——跨厂商调度 + 属于项目的账本与验收纪律。

**理由**：Harness 优化「一个 AI 怎么把活干好」，QW buddy 组织「活本身怎么被派发、验证、记住」。单厂商不会把「派活给竞争对手的产品」当作产品目标；Harness 的记忆属于它自己的产品，跨产品、跨天数的连续性不是它的业务。

**推论**：运行时里「派发」那一半**可能**被 Harness 吃掉（届时删掉即可），「账本 + 验收纪律」那一半吃不掉——这正是设计要把重量压在后者、把前者做薄的原因。

## 十二、MVP 边界（明确不保证什么）

**结论**：选择 **A**——只保证**存活且空闲的主控**能被唤醒；主控进程退出 / 整机重启后，由使用者重新启动主控，从账本续接。

**理由**：另一个选项（值守自动拉起主控）需要守护进程 + 会话恢复，属于重机械，与 MVP 冲突。审核指出「主控可死」与「使用者只提需求」两句必须二选一，本文件正式选定 A。

**代价（明示）**：半夜主控挂了，活会停在账本上，直到使用者回来重启主控。**不丢事，但可能停摆。**

## 十三、明确砍掉的（及原因）

| 砍 | 原因 |
|---|---|
| 项目注册表 / 克隆同步 / 上游同步 | 单项目形态下不存在 |
| 多机 secondmate | 单机单项目 |
| 常驻哨兵 / cron / 定时轮询 | 单人项目无场景，Herdr 事件替代轮询 |
| 对外通道（公开应答 / 语音 / 链路追踪） | 不需要 |
| 自更新 / 子代理副意识 / 各家产品钩子插件 | 运行时搬出 AI 后不需要 |
| 一切通知使用者的通道 | 睡觉不被打扰 |
| 唤醒队列 / ACK / 数据库 | 账本承担该职责（审核确认不必补） |
| no-mistakes 全流水线 | 改用项目自己的检查命令 |
| 其他终端后端 | 只用 Herdr |
| 角色切换流水账 | 产出物标角色即可 |

## 十四、审核修正（采纳情况）

独立审核（Astra / gpt-6-astra high）提出三条必须补、一条可砍、两条技术细节，全部采纳：

| # | 审核发现 | 处置 |
|---|---|---|
| ① | 账本路径必须唯一且工人与主控共读（副本里的 `tasks/` 主控看不到；原文还混用两个路径） | 采纳 → `DESIGN.md` §5 |
| ② | 唤醒不能是「一次性通知」，必须以**账本未结项**为准（主控忙 / 投递失败 / 值守重启都会丢） | 采纳 → `DESIGN.md` §4.3 |
| ③ | 「主控可死」与「使用者只提需求」必须二选一 | 采纳 A → `DESIGN.md` §10 |
| ④ | 角色切换不必单独记流水 | 采纳砍掉 → `DESIGN.md` §6、§11 |
| ⑤ | Herdr 超时单位是**毫秒**（`1800000`，不是 `30m`） | 采纳 → `DESIGN.md` §4.2 |
| ⑥ | `agent wait` 等的是**会话状态**，不等于验收成功，不能据此销账 | 采纳 → `DESIGN.md` §4.4 |

## 十五、与 firstmate 的关系

**结论**：借用 firstmate 的**机制思想**（唤醒主控、任务路由、额度判定、错题本、无状态主控），不搬其**实现**。

**理由**：firstmate 为「7×24 无人值守地盯一支船队」付出了约 8.7 万行脚本（其中运行时约 2.4 万行）；单项目、单人、有 Herdr 的场景下，绝大部分保险装置没有存在理由。QW buddy 保留其机制骨架，实现压缩到约 300 行脚本 + 数份说明文件。

**可回收利用的实物**：使用者现有项目（qonnwolfai-student）里已经在用的 `tasks/` 账本、任务书派发、`lessons/` 错题本、重启恢复手册——QW buddy 是把这些**手工约定固化成规范文件与脚本**，不是另起一套。
