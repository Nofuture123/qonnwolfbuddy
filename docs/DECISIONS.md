# QW buddy 决策记录

本文件记录每条设计结论、其理由，以及被否掉的替代方案。架构本体见 [`DESIGN.md`](DESIGN.md)，独立审核见 [`reviews/2026-09-15-astra-review.md`](reviews/2026-09-15-astra-review.md)。

记录日期：2026-09-14 ~ 09-15，与使用者逐步定案。

---

## 一、命名

**结论**：全称 `qonnwolf-buddy`（Q-Wolf Buddy），简称 **QW buddy**；机器场合（目录 / 命令 / 文件名）一律 `qwbuddy`。

**理由**：仓库名、命令行不接受大写与空格；人读场合需要可读的写法。二者是同一个名字的两种场合写法。

**否掉的**：`QW Mate`（早期误记，已废弃）；纯航海名（skipper / dinghy / coxswain 等，与品牌无关且 npm 多被占用）。

## 二、形态：装进项目，不是独立程序

**结论**：QW buddy = 一份说明书 + 几个 shell 脚本 + markdown 账本，**装进单个项目**；启动方式是在项目里开 Claude Code / Pi / Codex 并说「你现在是 QW buddy」。

**理由**：
- 使用者的真实场景是「在某个具体项目里干活」，不是「管一支船队」；
- 说明书由产品自身在会话开始时自动加载（`AGENTS.md` / `CLAUDE.md`），所以「变身」不需要任何额外程序；
- 单项目 = 天然轻：不需要注册表、不需要跨项目管理。

**否掉的**：
- **独立文件夹 + 管多个项目**（firstmate 形态）——使用者明确指出「太重」，且他不想要跨项目管理；
- **编译出来的独立软件**——多余；说明书 + 脚本已经能表达全部机制。

## 三、四大类机制

**结论**：记忆 / 规矩 / 保险 / 运行时。

**理由**：
- 使用者起初把「状态机」列为独立机制，后自行归入**记忆**——状态机本质是「跨会话记住活到哪了」；
- 对照 firstmate 的实体文件逐组盘点后，**唤醒机制不属于前四类中的任何一类**（它不是记忆、不是规矩、不是保险），它是让循环转起来的机器，因此单列「**运行时**」；
- 这一分类的意义在于**砍**：单项目下「运行时」是唯一能大幅瘦身的一类。

## 四、运行时：焦点是主控，不是执行层

**结论**：**运行时盯主控，不盯执行层。**

**理由**（使用者洞察）：
- 工人跑在 Herdr 窗口里，**Herdr 保证它一直跑到成功或失败**——派发与回读都不会卡；
- 唯一会「卡死」的情况是**主控没去看任务完成情况**——主控回合结束后不再回来；
- 所以运行时的职责是「让主控不必记得去看 / 忘了也能被叫回来」。

**否掉的**：把运行时做成 firstmate 那样的「盯工人」系统（巡检各窗口、判定 stale、唤醒队列、ACK 协议）——那是 2.4 万行的来源，且盯错了对象。

## 五、运行时演进（三次，含一次纠错）

| 阶段 | 结论 | 理由 |
|---|---|---|
| ① | 前台等待（主控阻塞等工人跑完） | 最省机器；**但被否**：工人要跑在 headless 模式才能同步等，而使用者要求看得见 |
| ② | Herdr 窗口 + 事件驱动（`herdr agent wait` / `pane wait-output`） | 用 Herdr 的**阻塞等待**替代轮询：不空转、不耗算力、不需要给每家产品写钩子 |
| ③ | **值守脚本必须存在**——它的唯一动作是**叫醒主控** | ②曾被我一路砍到「两个脚本、零值守」，**这是砍错了**：使用者的头号需求就是 firstmate 的**主控唤醒机制**（连最强模型作主控也会「叫不醒」）。修正：值守回来，但只叫醒主控 |

## 六、「叫醒主控」≠「通知使用者」

**结论**：**零通知使用者**；**必须有叫醒主控**。

**理由**：两者被我早期混为一谈。使用者明确：睡觉时不想被任何东西打扰（钉钉、系统通知一律不要）；但他需要主控自己回来干活。所以：

| 动作 | 是否保留 |
|---|---|
| 叫醒使用者（钉钉 / 通知 / 弹窗） | ❌ 全部砍掉 |
| 叫醒主控（`herdr agent prompt <主控窗口>`） | ✅ 保留，是运行时核心 |

**否掉的**：钉钉通道（使用者明确否决，且其场景是「睡觉不被打扰」）；`herdr notification` 等一切面向人的推送。

## 七、验收权下放给主控

**结论**：**使用者只提需求**；哪些需要审核、哪些不需要、验收通过后怎么落地，全部由主控判断与执行。

**理由**（使用者原话）：他不是唯一的验收人；他选推理能力强、知识面广的模型作主控，因为它对程序的理解比他强；连超时/卡死也归主控判断。

**必带的保险**：**验收必须留证据**——主控把「跑了什么检查、结果、结论」写进账本（含主控自干的小活）。可能永远没人看，但必须留，使权力下放**可审计**。

**否掉的**：把使用者当唯一验收人（我最初的错误假设，已被使用者纠正）。

## 八、不设常驻岗位，动态组队

**结论**：默认**一个全栈工人包干**；大活按**模块**拆并行（不按前端/后端拆）；每次交付配**独立验收 agent**（唯一值得专职的角色）；架构按需**临时**评审 agent，审完即散；CI/CD 交**脚本**。不设常驻架构师 / 前端 / 后端。

**理由**：
- AI 没有「手艺生疏」问题，都能写全栈；按技术栈拆会让一次跨层改动被割裂成两半、通过文件传话，最容易丢信息；
- 人类团队的分法是按**职位**分；AI 该按**改动边界**与**职责性质**分；
- 唯一真实的对抗关系是「写实现的人 vs 挑错的人」——所以独立验收 agent 值得专职，这也正是 firstmate 独立审查的原理。

**否掉的**：照搬人类团队结构（架构师 / 前端 / 后端 / 测试 / CI-CD 五个常驻角色）——会产生空转岗位与上下文割裂；CI/CD 本来就不需要 AI。

## 九、身份切换

**结论**：角色 = 独立说明书文件（`roles/` 四份）；切换 = 一句话；产出物标注角色。

**性质限制**（审核认定）：
- 只是**行为约定**，不是权限隔离，也不清空上下文；
- 根级说明书的固定禁令**不可被角色文件推翻**；
- **同一会话换角色 ≠ 独立审核** → 「审核必须换模型家族」保留为硬规矩。

**否掉的**：每次切换单独记流水账——产出物标角色即可（审核建议，采纳）。

## 十、工人与主控的产品选择

**结论**：
- **工人**：Codex / Pi / Claude Code 三家；**一律在 Herdr 窗口里交互式运行**；**禁用 headless**。
- **主控**：首选 Claude Code；说明书**产品中立**，Pi / Codex 也能当主控，零新代码。
- **不用**：Cursor、Kimi、Rovo 等。

**理由**：
- 使用者要求「看得见子任务运行情况」——这是 Herdr 带给他的确定好处；
- 产品中立让主控**可以随时换人**，因为状态在账本里而不在模型脑子里；
- 三家之外的产品没有实际使用场景，支持它们只会复制 firstmate 的「每家一根线」问题。

**否掉的**：headless 工人（使用者明确否决）；「每家产品写一套钩子 / 插件」（运行时搬出 AI 后不再需要）。

## 十一、Harness 边界（为什么这东西不会被淘汰）

**结论**：两条尺子——

1. **谁的状态**：状态属于**产品**（会话 / 模型 / 厂商）→ 交给产品；属于**使用者与项目**（任务 / 验收 / 教训）→ 放在产品外面（我们这层）。
2. **薄即抗淘汰**：Harness 会越来越强，吃掉「等待、通知、记忆」；QW buddy 只持有它吃不掉的——跨厂商调度 + 属于项目的账本与验收纪律。

**理由**：Harness 优化「一个 AI 怎么把活干好」，QW buddy 组织「活本身怎么被派发、验证、记住」。单厂商不会把「派活给竞争对手的产品」当作产品目标；Harness 的记忆属于它自己的产品，跨产品、跨天数的连续性不是它的业务。

**推论**：运行时里「派发」那一半**可能**被 Harness 吃掉（届时删掉即可），「账本 + 验收纪律」那一半吃不掉——这正是设计要把重量压在后者、把前者做薄的原因。

## 十二、MVP 边界（明确不保证什么）

**结论**：选择 **A**——只保证**存活且空闲的主控**能被唤醒；主控进程退出 / 整机重启后，由使用者重新启动主控，从账本续接。

**理由**：另一个选项（值守自动拉起主控）需要守护进程 + 会话恢复，属于重机械，与 MVP 冲突。审核指出「主控可死」与「使用者只提需求」两句必须二选一，本文件正式选定 A。

**代价（明示）**：半夜主控挂了，活会停在账本上，直到使用者回来重启主控。**不丢事，但可能停摆。**

## 十三、明确砍掉的（及原因）

| 砍 | 原因 |
|---|---|
| 项目注册表 / 克隆同步 / 上游同步 | 单项目形态下不存在 |
| 多机 secondmate | 单机单项目 |
| 常驻哨兵 / cron / 定时轮询 | 单人项目无场景，Herdr 事件替代轮询 |
| 对外通道（公开应答 / 语音 / 链路追踪） | 不需要 |
| 自更新 / 子代理副意识 / 各家产品钩子插件 | 运行时搬出 AI 后不需要 |
| 一切通知使用者的通道 | 睡觉不被打扰 |
| 唤醒队列 / ACK / 数据库 | 账本承担该职责（审核确认不必补） |
| no-mistakes 全流水线 | 改用项目自己的检查命令 |
| 其他终端后端 | 只用 Herdr |
| 角色切换流水账 | 产出物标角色即可 |

## 十五、与 firstmate 的关系

**结论**：借用 firstmate 的**机制思想**（唤醒主控、任务路由、额度判定、错题本、无状态主控），不搬其**实现**。

**理由**：firstmate 为「7×24 无人值守地盯一支船队」付出了约 8.7 万行脚本（其中运行时约 2.4 万行）；单项目、单人、有 Herdr 的场景下，绝大部分保险装置没有存在理由。QW buddy 保留其机制骨架，实现压缩到约 300 行脚本 + 数份说明文件。

**可回收利用的实物**：使用者现有项目（qonnwolfai-student）里已经在用的 `tasks/` 账本、任务书派发、`lessons/` 错题本、重启恢复手册——QW buddy 是把这些**手工约定固化成规范文件与脚本**，不是另起一套。

## 十六、worktree 收尾规范（采纳外部建议）

**结论**：四步规范（开 / 收·成功 / 收·废弃 / 留·例外）+ 两条补充（谁派生谁收尾、`git worktree prune`）。见 `DESIGN.md` §3.2。

**来源**：使用者提供的网络建议（清点提示词、清理提示词、AGENTS.md 规则），评估后合并采纳。

**为什么采纳**：本设计原有「未落地的工作绝不删」——安全但有死角：**工作一旦被放弃，就既删不掉也不会落地**，只能永远占着目录与分支。外部建议的「**先提交 → 打 `archive/<任务>` 标签 → 再删 worktree 与分支**」补上了这个死角：工作完整留在 git 历史里（可找回），目录与分支则清掉。

（附一次实证：本项目早期一次失败派工在 `~/.treehouse` 留下了一个空壳池目录 `qonnwolfbuddy-c07e2a`——已验证其中无 worktree、无未落地内容后清除。**注意：不应把「看起来旧」当成垃圾的证据**——使用者的 `qonnwolfai-student` 下几个 worktree 曾被我误判为残留，实际当天仍在提交使用中。）

**对建议的两处修改**：
1. 「同步到 main 就直接删」→ 必须核实**真的落地**（已合并/已推送），且删除前先检查有无未提交改动。
2. 「不确定的给我确认」→ 按本项目**零通知**的设计，改为「记进账本，使用者回来一次看」。

**落地位置**：`DESIGN.md` §3.2；使用者全局规则 `~/.pi/agent/AGENTS.md`。

## 十七、唤醒闭环修订（Astra medium 审核后，2026-09-15）

**结论**：审核四条发现（致命 2 / 必须补 2）全部修复，落地提交 `6d90438`，验收通过。

| # | 审核发现 | 严重度 | 处置 |
|---|---|---|---|
| F3 | 去重键只挂 `state:`，而 `state:` **只有主控能改**（工人只追加状态行）→ 工人完成后**永久不再叫醒主控** | 致命 | 去重键改为**进展指纹** `sha1(state + 最后一条状态行)`；工人写 `done:`/`blocked:` 指纹即变 → 重新叫醒。见 `DESIGN.md` §4.3 |
| F4 | `herdr pane run` 失败在 `set -e` 下**终止整个值守** | 致命 | 失败不写 `wake:` 行（下轮重试）、报 stderr、继续下一项、主循环不退出 |
| F2 | 值守取**第一条** `dispatch:`（不筛未结任务、不取最新），失效 pane 被 `\|\| true` 吞掉 → **忙循环**（审核实测 5 轮 0.072 秒） | 必须补 | 只取**未结项**任务书的**最新** `dispatch:`；等待失败退化为按 interval 等待 |
| F1 | `DESIGN.md` §3.3 承诺的「锁」无定义、无实现（「护栏」同样只是角色约定） | 必须补 | 最小实现 `bin/qwb-lock.sh`（`mkdir` 原子目录锁）；「护栏」在 §3.3 明确为**行为约定**而非代码机制 |

**根因归属（不粉饰）**：F3 是**主控的规格错误**——第一版任务书把「未结项」与「去重键」都只挂在 `state:` 字段上；F4/F2 是实现偏离既有设计意图；F1 是设计承诺未定义。

**教训（已入错题本）**：**去重键不能挂在一个「只有单方能改」的字段上**。判断「有没有新变化」必须基于**真正会变化的那一方**产生的信号——这里工人只会追加状态行，所以指纹必须包含状态行。

**审核质量问题**：Astra medium 的四条发现全部经主控**独立复现**成立（含忙循环计时、投递失败退出码、指纹不变导致漏叫），且给了函数级替身复现方法。审核有效。

## 十八、复核四发现修订（Astra medium 复核后，2026-09-15）

**结论**：复核四条（致命 1 / 必须补 2 / 可以不要 1）全部修复，落地 `fbe27c0`，验收通过。

| # | 复核发现 | 严重度 | 处置 |
|---|---|---|---|
| G1 | **detached HEAD 下归档/落地对象错位**：worktree 在分支 `T` 的提交 A 上 `checkout --detach` 并产生提交 B 后，`--archive` 打的标签指向 **A**、`--merged` 按 A 判断 → **实际工作 B 丢引用，且拒绝条件可被正常 detach 操作绕过** | 致命 | 一律以 **worktree 当前 HEAD 的实际提交 OID** 为判断与归档对象；detached 时标签指向实际工作且**不删**指向别处的同名分支；`git status` 失败视为状态未知 → 拒绝 |
| G2 | 等待路径重复等待：`agent wait` 超时后**又 sleep 一个完整 interval**，实际延迟 ≈ 2×interval（`DESIGN.md` §10 声称 1×） | 必须补 | 一轮总耗时预算 = 约 1×interval；等待已耗掉的时间计入预算，只有**立即失败**才 sleep 防忙循环 |
| G3 | 配置读取仍是「正则猜 JSON」：`--worker workers` / `'(codex)'` 可绕过校验、单行 JSON 误拒、**顶层同名键静默抢走**（实测读到 `interval=9`、`pane=wtest:wrong`） | 必须补 | **换掉根因**：配置改为 bash 可直接 `source` 的单一来源 `templates/config.sh`，**删除 `config.json`**；工人名按 `QWB_WORKERS` 整词精确匹配。零解析、零依赖、零歧义 |
| G4 | `--keep` 被脏检查挡住，排除了 `QWBUDDY.md` §6 明确允许的「有冲突待解」保留 | 可以不要（但与规范冲突） | 脏检查只用于会删东西的 `--merged` / `--archive`；`--keep` 不做脏检查 |

**为什么 G3 不选「更严格的正则」也不引 jq**：上一轮只修了 `note` 个例、没修根因，同类缺陷第二次出现。**bash `source` 的配置文件比任何 JSON 解析都薄**（少写解析代码，且不可能解析错），与项目「零钩子、零插件、零外部服务」一致。代价：放弃 JSON 的工具友好性——但配置只被自家脚本读，没有实际用户。

**审核有效性**：复核抓到的都是**主控 86 项冒烟断言完全没构造过的场景**（正常 detach 绕过拒绝条件、跨段误读、单行 JSON）。**对抗性审核（换模型家族 + 自己构造场景）是主控自建门不能替代的**。

处置（`spec-resolved:`）才能解除；普通 `working:`/`done:`/`dispatch:` **不能解除**；处置后**新疑点重新拦截**。`qwb-status.sh` 用同一判定显示「规格疑点未处理」（**不被后续普通日志遮住**）。审核者角色文件新增「审票（按需）」三审点：票内部与上游承诺是否一致 / 场景是否覆盖这次反例与失败路径 / 验收门能否对已知错误**实际失败**。

**过程中的重要发现**：实现后主控验收抓到一条**主路径 bug** —— `--revise-scenarios` 改完场景要继续派发，而**首次派发已建 `<项目>/.worktrees/<任务id>`** → 二次派发（**返工也走这条路**）撞 `already exists` → `git worktree add` 失败退出。修法：隔离副本**幂等复用**（`wt_is_valid` 双条件：`rev-parse --show-toplevel` 物理路径相等 + `worktree list --porcelain` 查得到），存在且有效则复用、脏目录仍拒绝。

**执行者接力**：zcode（GLM-5.3-Flash，因免费额度限流+主控发现 bug）→ pi（deepseek-v4.1-flash，补返修）→ devin（SWE-2 Max，核对确认+全量独立验证）。**三方自述一律不采信**，主控全部门与反例自己重跑（`full` **328 PASS / 0 FAIL**；自做反转验证：改坏幂等判定 → smoke **6 条变红**）。

**这套机制自己的边界（Astra 明说，照录）**：① **所有参与者都没意识到规格可疑时，它不会自动发现**；② 「在已有窗口直接继续派实现」仍**依赖主控守约**（本轮不扩成通信拦截器）。它消除的是「疑点已提出却照旧重派」这类**机械失误**，不承诺自动诊断所有坏票。

## 二十七、工人 tab 落在项目 workspace，不是主控所在的 workspace（2026-09-16）

**缺陷**：`qwb-run.sh` 与 `qwb-wake.sh --ensure` 调 `herdr tab create` 时不传 `--workspace`，herdr 把 tab 落在**调用者所在** workspace。主控与项目同 workspace 时无感；主控跨项目派活（在 wA2 给 wA3 的项目派）时，工人窗口出现在主控身边，**项目的 workspace 里什么都看不到**。2026-09-16 实测：`worker-launch-modes` 的工人开在 `wA2:t3`，两次 E2E 临时项目的工人开去了 `w8Z`。

**决定**：新增 `qwbuddy/bin/qwb-lib.sh`（**库文件，不直接运行**，被 run/wake source）提供 `resolve_workspace <项目根>`，三级解析、取第一个命中：

1. `config.sh` 的 `QWB_WORKSPACE` 非空即用；**本机 herdr 查不到该 id → 拒绝派发**并提示改 config。不静默回退——声明写错了就把错误暴露出来，别把工人送到别处。
2. 空 → `herdr workspace list` 里 `worktree.repo_root` **物理路径**（`realpath` 归一，吃掉 `/tmp`↔`/private/tmp` 这类符号链接差异）等于项目根的那一项。多于一个匹配取 `focused` 的；都不 focused 取第一个并 stderr 警告。
3. 都没有 → 现状（不带 `--workspace`，即调用者 workspace）+ stderr 一行警告「未声明 QWB_WORKSPACE」。

**为什么按 repo_root 匹配只能当次选**：真录（`tests/fixtures/herdr/workspace-list.json`）显示 `worktree` 字段**只有部分 workspace 有**（w8Z/wAB 有，wA2/wA3 没有——取决于该 workspace 怎么建的），所以「按 cwd 猜」不可靠，只能当 `QWB_WORKSPACE` 未声明时的兜底。**主路径是靠声明**。

**接线范围**：`qwb-run.sh` 在**任何副作用（锁/worktree/tab/账本写）之前**解析，失败即拒绝；`--pane` 复用路径不建 tab（pane 已定），不解析、不受影响。`qwb-wake.sh` 只改 `--ensure` 里唯一的 `tab create` 那一处（复用既有 pane / 原地重启的分支不建 tab，不解析），并把解析出的 id 记进 `.watch` 的 `workspace=`。**不做**自动建 workspace——找不到就按上面三级规则处理。

**响应防御**：`workspace list` 用 `perl -MJSON::PP` 解析，`workspace_id` 必须是非空 JSON 字符串（对象/数组/数字/布尔/null 一律判整体失败，R2-M2 同款）；查询失败与响应不合契约都在副作用之前非 0 退出（fail-closed）。stub 应答取自真录，测试用 `perl` 以真录为底稿只改 `repo_root` 指向来构造「唯一匹配/多匹配/都不 focused」三形态，不硬编码 JSON。

**既有安装副本要更新**：`qwb-lib.sh` 是新增文件，已装过的项目需重跑母本仓 `bin/qwb-init.sh`（幂等，按 `bin/qwb-*.sh` 全量复制）才补得上；没补上时 run/wake 直接**报错退出并指名重跑 init**，不退回旧行为（宁可不派发，也不把工人静默送到别处）。

**验证**：`tests/smoke.sh` 新增第 48 节（10 条断言：票 §1 的 8 条场景 + 查询失败/错型响应两条负例，含 `--ensure` 同款与「恰一行警告」计数断言）；`fast` 门 rc=0；`full` 门 rc=0、**440 PASS / 0 FAIL**（smoke 418 + review-identity 15 + lint 7）。真机 E2E 由执行者跑（工人 tab 实测落在 `QWB_WORKSPACE` 声明的 wAC，而执行者在 wA3），主控复验见任务书状态行。

## 二十八、工人与审核者一律最高权限启动（`QWB_WORKER_ARGS`）——为什么最高权限、为什么两个键（2026-09-16）

**缺陷（实测）**：`qwb-run.sh` 起工人是裸命令——`herdr agent start <NAME> --kind <工人> --pane <PANE>` 不带任何 agent 参数。工人因此在**默认权限模式**下跑：每个写文件、每条命令都可能弹审批框，而窗口里**没有人点**，工人就卡在那里不动。2026-09-16 主控手工派 cmd 时先卡在信任框上，Rocky 当场要求改成 `cmd --yolo --trust` 重开。

**决定**：**工人与审核者一律最高权限启动**（Rocky 2026-09-16：「所有工人和审核全部按最高权限开启 cli」）。herdr-kind 工人在 `QWB_WORKER_ARGS` 里按工人配参数，pane-run 工人在 `QWB_WORKER_LAUNCH` 命令行里配。

| 工人 | 参数 | 备注 |
|---|---|---|
| codex | `--dangerously-bypass-approvals-and-sandbox` | 等价 `-s danger-full-access -a never` |
| claude | `--dangerously-skip-permissions` | |
| devin | `--permission-mode dangerous` | dangerous 自动批准全部工具 |
| omp | `--auto-approve` | |
| pi | `--approve` | 只有「信任项目文件」；pi 是否另有工具审批由执行者真机核实 |
| cmd | `--yolo --trust` | 写在 pane-run 命令行里；`--trust` 同时消掉新目录信任框 |
| zcode | 无 | `zcodecli chat` 本身是 yolo 模式 |

**为什么最高权限是对的（审批在这里没有增益）**：工人跑在**隔离 worktree** 副本里，改动由主控合并落地；产物**由主控独立验收**（`QWBUDDY.md` §5：不采信工人自述）。审批的收益是「拦下不该做的动作」，而这个动作的**实际效力**已经被两道门拿走了：可回滚的隔离副本 + 主控验收。剩下能拦住的只有**工人自己的手滑**，代价却是**整条流程被一个没人看的提示框冻住**——而冻住本身是不安全的：它让「工人卡死」与「工人在干活」在账本上长得一样，靠 `QWB_REWAKE_MS` 兜底才发现。所以这里是**用「可回滚 + 独立验收」换「无人值守能跑通」**，不是省事。

**不做的事**：不给**主控**自己加权限参数——主控是使用者自己起的会话，不归 QW buddy 管（`qwb-run.sh` 只起工人；审核者作为工人被派发时同样走这张参数表）。

**为什么与 `QWB_WORKER_LAUNCH` 分成两个键**（同一份解析实现、两个用途）：

1. **一个管「起什么」，一个管「带什么参数」**。`QWB_WORKER_LAUNCH` 回答「这个工人用 `herdr agent start` 还是 `pane-run:<命令>`」，`QWB_WORKER_ARGS` 回答「以什么参数起」。这两件事的**变化节奏**不同：权限参数是全局一致的默认值，启动方式只在某家 CLI 不被 herdr kind 支持时才需要覆盖。
2. **herdr 模式的起法固定，只差参数**。`herdr agent start <NAME> --kind <工人> --pane <PANE> --timeout <ms> -- <参数>` 对每个 `--kind` 都是同一条命令；把参数挤进 `QWB_WORKER_LAUNCH` 只会让「启动方式」这个字段同时承担两种语义，`herdr` 这个默认值也没法再表达「用 herdr 起、但带参数」。
3. **pane-run 的参数必须在命令行里**。pane-run 跑的是配置写的**一整条命令**（`cmd --yolo --trust`），参数与命令不可分，塞进 `QWB_WORKER_ARGS` 反而要再造一套「往命令行尾部插词」的规则。因此**一个工人的启动参数只能有一处**：pane-run 工人在 `QWB_WORKER_ARGS` 里配了值 → **拒绝派发**并指回去写 LAUNCH（配置错了就报错，不猜、不合并、不静默忽略）。

**实现要点**：两张表**共用同一个解析函数**（`worker_map_get`，格式 `工人名=值`，值可含空格、遇下一个「工人名=」前缀才结束，同一工人取最后一项），不写第二份；解析结果经全局回带（`WORKER_MAP_FOUND` / `WORKER_MAP_VALUE`）而不用命令替换，以便区分「未列出」与「列出但值为空」。参数串**按空格切词**追加到 `--` 之后，**不做 shell 引号解析**（需要带空格的单个参数时用 pane-run 命令行）；空值 → 不加 `--`，与不配置时**字节一致**。herdr 与 pane-run 两条路的 headless 禁令（`-p`/`--print`/`--exec`/`exec`）**共用同一条检查函数**；两类拒绝都发生在**锁/worktree/tab/账本写之前**（零副作用）。

**格式的隐含耦合（真机实测发现）**：「值遇下一个 `工人名=` 才结束」里的**工人名取自 `QWB_WORKERS`**，因此一条 `QWB_WORKER_ARGS` 表只有在该表用到的名字**都在工人表里**时才切得对——名字不在工人表里的那一项会被当成上一个值的续词。模板默认工人表原是 `codex pi claude`，而默认 ARGS 表还含 `devin=`/`omp=`，两者不自洽时 `claude` 会多收到 `devin=--permission-mode dangerous omp=--auto-approve` 两个废词（真机 pane 回显可证：`claude --dangerously-skip-permissions devin=--permission-mode dangerous omp=--auto-approve`）。**处置（主控裁定 spec）**：默认工人表同步扩为 `codex pi claude devin omp`——两条默认值必须自洽，装出来的项目才对这五家都成立。否掉的替代：**少列**（默认 ARGS 只写 `codex=`/`claude=`/`pi=`）等于装出来的项目一旦加用 devin/omp 就裸跑；**加解析后校验**（值里出现 `名字=` 而该名字不在工人表就拒绝）会误杀合法参数——`codex -c model=o3` 这种值本身就含 `name=` 形式。耦合本身留作格式的既定语义（值里带 `名=` 的单个参数要用 pane-run 命令行写）。

**不动的**：`qwb-init.sh` 不改——新装项目直接拿模板默认值；已装项目由主控手工往 `config.sh` 补键（`qwb-init` 不覆盖已有 `config.sh` 是既定行为）。`dispatch:` 行格式不变；参数不写进账本（要审计看 `config.sh`）。`QWBUDDY.md` §10 硬规矩不加条——这是配置默认值，不是禁令。

**验证**：`tests/smoke.sh` 新增第 49 节；`fast` / `full` 门结果与真机 E2E（codex / claude / pi 真派票、贴 `herdr pane read` 原文确认无审批框、临时项目用完即清）见 `tasks/2026-09-16-worker-max-permission.md` 的状态行。

## 二十九、值守隐形化：按主控 harness 接值守，可见 tab 降级为 fallback（2026-09-23）

**来源**：使用者「firstmate 就没有值守窗口」——QW buddy 的值守此前只能在主控 workspace 开一个可见 shell tab 死循环，Rocky 不想要这个窗口。

**结论**：值守改按主控 harness 各接一套，共用一个核心：

| 主控 | 接法 | 共用核心 |
|---|---|---|
| Claude Code | `.claude/settings.json` 的 **Stop hook**（`asyncRewake: true`，timeout 7200 **秒**），由 `qwb-init.sh` 幂等合并；hook 守卫（仅主控锁 pane）+ `.hook.lock` 单飞后前台跑 `qwb-wake.sh --block` | `qwb-wake.sh --block [--max-ms <毫秒>]` |
| Codex | **前台 checkpoint**：开局后把 `qwb-wake.sh --block --max-ms 180000` 当前台 tool call 循环（exit 2 处理账本 / 124 再跑 / 0 收工）；禁止 `&` 后台 | 同上 |
| 其他/未知 | `--ensure` 可见值守 tab（保留，fallback） | 现有循环模式 |

**§10.2「无守护进程」的边界（正式裁定）**：**由主控进程拥有、随主控死**的值守子进程（Stop hook 的 `--block`、Codex 前台 checkpoint、可见 tab 里的循环）不算守护进程——它们没有独立于主控的生命周期，不违背「无守护进程」的本意（无人看护的常驻进程）。仍然禁止 cron / launchd / systemd / 独立 nohup 进程。MVP 保证随之升级为「存活且空闲的主控能被叫醒，且不要求任何可见窗口」。

**为什么 hook 语义必须三方核实而不是照抄 firstmate**：官方文档实核（claude 2.1.278 + code.claude.com/docs/en/hooks.md）修正了两处容易转述错的地方——① hook 的 `timeout` 字段单位是**秒**（"Seconds before canceling"），与本项目「超时一律毫秒」并存不冲突（`QWB_HOOK_MAX_MS=7200000` 毫秒 ↔ settings.json `timeout: 7200` 秒，同一时长的两种单位）；② `asyncRewake` 的摘要交付通道是 **stderr 优先、stderr 空才退回 stdout**，所以 hook 把摘要 stdout/stderr 双写，两条通道任一生效都能到模型。文档同时证实 async hook「每次 Stop 都触发、不去重」——`.hook.lock` 单飞是必须的，不是过度设计。真机 E2E 见任务书状态行。

**退出码契约**（block 模式，供所有主控 harness 复用）：2 = 有可动作变化（stdout 摘要 + 票末追加 `wake:` 行）；0 = 账本无未结项（不写任何行）；124 = `--max-ms` 到期无变化（不写任何行，GNU timeout 惯例，同 firstmate checkpoint）；其他非 0 = 错误。去重与 `QWB_REWAKE_MS` 时间兜底与循环模式完全共用（`wake:` 行记在同一本账本上，两种值守形态不会互相重复叫）。


## 三十、收敛审核修复：残留锁自动回收 / 一轮一条投递 / REWAKE 只对 running / 工人丢失入指纹 / worktree 初始化钩子（2026-09-21）

**来源**：2026-09-21 主控收敛审核（发现 A1/A2/A3/A4/P1-2/P3-agent 名），五处实测缺陷的取舍记录。

**B · 残留锁自动回收为什么是「判活」而不是「超时」**：锁残留的根因是锁主会话死亡（Claude Code 重启、换 pane），而锁主身份（`pid:<n>` / herdr pane id）本身就是可查的活性证据——pid 用 `kill -0`，pane 用 `herdr pane get`。按「锁主死了才回收」回收，天然不需要超时参数，也不会夺活人的锁；超时夺锁则要么误夺长跑主控、要么留死锁太久。判不出死活（herdr 不在 PATH、查询报错、owner 文件缺字段）一律**拒绝不回收**（fail-closed）——宁可让人工 `release`，不猜。否掉的替代：`--force` 夺锁（让「绕过另一个活主控」变成一键操作，与锁的本意矛盾）。

**C · 值守为什么一轮只发一条投递**：旧实现每张未结票各发一条 `pane run`，主控一个回合收 N 条消息、每条都只说「请读 tasks/」；生产项目 tasks/ 有 282 个文件，等于叫醒后让人重读整个账本。改为把本轮所有「要叫」的票拼进**一条**文本（各票文件名、state、最后状态行截 160 字符），主控一个回合拿全上下文。投递成功才逐票写 `wake:` 行、失败一行不写——保持「投递失败=未叫」的原语义，避免部分叫醒部分没叫的去重黑洞。**REWAKE 只对 running**：时间兜底的设计目的是「工人挂起没写行」，这个前提只在 running 成立；blocked/needs-decision 等的是主控裁决或使用者，指纹未变还重叫只是烧 token。`--block` 的孤儿复核（锁不在手即 exit 0）与 hook 自身的守卫重复，但两处都留：hook 是唯一入口的当下是双保险，Codex 前台 checkpoint 等直跑 `--block` 的入口只有这一道。

**G · 工人丢失为什么拼进指纹而不是单独叫一次**：重派提示需要一个「会停」的信号源——若丢失单独触发叫醒，跟指纹去重是两套账，会出现反复叫或永不叫。拼进指纹（`state\n最后状态行\nlost=<pane>`）后复用同一套去重：工人一消失指纹变一次叫一次，工人复活或重派后再变一次，之后安静。判定只认 `pane_not_found` 与「pane 在但 agent 空」两种可证实状态；查询失败显示「工人状态未知」不当丢失（不猜）。

**D · `QWB_WORKTREE_SETUP` 为什么放 config 而不是任务书**：装依赖（pnpm install、拷 .env）是**项目属性**不是任务属性——每张票都一样，写任务书会让 282 张票各抄一遍、漏抄即翻车；放 config 一处声明，`qwb-run.sh` 在新建副本后、开 tab/记账前执行，失败拒绝派发（副本保留排查，账本零副作用）。只对新建副本执行：复用副本意味着依赖已在，重装只浪费时间。

**E · agent 名兜底只取 sha1 前 8 位**：中文任务 id 净化后剩 `qwb--01` 这类残渣、两票同名；sha1 前 8 位（16^8 ≈ 43 亿）对单机同时存在的 agent 数足够，且比「要求所有任务 id 都 ASCII」少一条新规矩。只对未显式给 `--name` 的派发生效——显式指定是主控的意志，不覆盖。


## 三十一、安装收尾与派发补漏：运行态 .gitignore / dispatch-rules 落点 / 双配置守卫 / 开局点名用 status / 重派复用工人（2026-09-21）

**来源**：2026-09-21 主控收敛审核对照生产项目 `qonnwolfai-student` 审出的安装问题（P1-3/P1-4/P2-母本仓/token-开局/重派副作用）。

**A · 运行态为什么不进项目的 git**：`.worktrees/<id>/`（内含嵌套 `.git` 文件）、`qwbuddy/.controller.lock/`、`.watch`、`.watch.lock/`、`.hook.lock/`、`.hook.err` 全是运行态，留在 `git status` 里会污染项目、干扰主控验货时的脏检查。`qwb-init.sh` 往 `<项目根>/.gitignore` 追加一段带标记行的段（幂等：有标记行跳过、无文件新建），只追加不重排——项目原有条目字节不变。否掉的替代：只 ignore `qwbuddy/` 整目录——会把项目主人可能想跟踪的 `qwbuddy/brief-include.md`、`config.sh`、规则文件也藏掉，过度。

**B · dispatch-rules 为什么落 `qwbuddy/` 而不是根 `config/`**：生产项目根的 `config/` 是 app 自己的目录，QW buddy 其余文件全在 `qwbuddy/` 下，没有理由为这一条规则文件开例外；且 init 此前不拷模板，装完 `--worker auto` 永远 `no rules`。路径改 `<项目根>/qwbuddy/dispatch-rules.json`，init 拷模板（目标已有不覆盖，同 brief-include 纪律）。否掉的替代：旧路径兼容回退——功能 2026-09-17 才合入、无外部安装，兼容层是白背的复杂度，还会让「两处规则文件哪份生效」变成新的排查题。

**C · 母本仓双配置守卫**：母本仓自己既有跟踪的 `qwb.config.sh`，又有主控开局建的未跟踪 `qwbuddy/config.sh`（锁/值守要 `qwbuddy/` 目录），`qwb-test.sh` 优先读后者——改前者的质量门不生效且无人知道。处置：母本仓 `.gitignore` 加 `qwbuddy/`（该目录在母本仓只是主控运行态，明说不装自己）；`qwb-lint.sh` 新增母本仓布局专属检查——两份配置同时存在时 `QWB_GATE_FAST`/`QWB_GATE_FULL` 必须一致，否则 FAIL 并打印两边的值；只有一份配置时不适用、不输出。否掉的替代：禁止主控在母本仓开局抢锁——值守确实需要 `qwbuddy/`，禁不掉，只能把不一致变成看得见的 FAIL。

**D · 开局点名为什么改成跑 `qwb-status.sh`**：生产项目 tasks/ 有 282 份文档，让主控模型自己列出全部任务书再逐份读 `state:` 是纯 token 浪费；`qwb-status.sh` 已经输出未结项、最近状态行、规格疑点、值守健康与工人丢失。QWBUDDY.md §1 第 2–5 步合并为「跑 status → 只读未结项那几份的末尾状态行 → 报告」，两份 hook 模板第 2 条同步。不改任何脚本。

**E · 返工重派为什么复用同名工人而不是总开新窗口**：错题本已有「执行者产物的修订退回执行者窗口」；现实中重派常因原 agent 还在（done/idle）而撞 `agent_name_taken`，留下死 dispatch 行和空 tab。`qwb-run.sh`（herdr 模式）开 tab 前先 `agent get <名字>`：idle/done → 复用（不建 tab、不 start，直接 prompt 续派，dispatch 行写它现有 pane）；working/blocked → 拒绝（工人还在干，别打断）；查询失败 fail-closed 拒绝。新开路径 `agent start` 失败 → 关刚建的 tab、回滚刚写的 dispatch 行（只删最后一行且必须是本次写的那行）、exit 1 上报原始错误——派发失败不留半截副作用。pane-run 模式不动（它本来就没有 agent 名字池）。
## 三十二、Pi 主控值守走扩展而非窗口/checkpoint（2026-09-23）

**来源**：值守隐形化补齐第三种主控——pi 没有像 Claude Code 的 Stop hook、也不能像 Codex 那样当前台 tool call 循环，但 pi 有扩展机制（`session_start` / `session_shutdown` / `turn_end` 事件 + `pi.sendUserMessage(content, { deliverAs: "followUp" })` 注入）。

**结论**：Pi 主控值守装成项目级扩展 `.pi/extensions/qwb-watch.ts`（`qwb-init.sh` 安装），由扩展持有 `qwb-wake.sh --block` 阻塞子进程：exit 2 → stdout 摘要以 `[qwb-wake]` 前缀 follow-up 注入并立即重启下一轮；exit 0 → 清 `.watch` 闲置，`turn_end` 用 `--block --max-ms 1` 探测（0/124 判定有无未结项，不另写账本解析）；其他退出码 → 记 `qwbuddy/.pi-watch.err` 指数退避（上限 `QWB_WAKE_INTERVAL_MS × 8`），退避到顶注入一次「值守故障」叫醒主控去修。

**为什么是扩展而不是另开窗口或让模型轮询**：已经有后台注入能力（`sendUserMessage` + `followUp`）就不该让模型轮询——轮询烧 token、抢回合；窗口形态违背「值守隐形化」的初衷。扩展持有的子进程随 pi 进程生死（spawn 不 detach + `session_shutdown` 杀 + `process exit` 保底），不是守护进程，符合 §10.2 的边界裁定。锁主复核（`.controller.lock/owner` 末字段 == `HERDR_PANE_ID`）决定扩展是否值守：非主控的 pi 会话一律不动，与 `--block` 的孤儿复核同判定。

**与 firstmate 的边界**：只取「持子进程 + follow-up 注入」这一个机制；不搬分支监督、lease、generation ledger、远程 secondmate。Pi 扩展 API 以官方文档实测为准（本机 pi 0.86.1，`extensions.md`：`session_start`/`session_shutdown`/`turn_end` 事件、`pi.sendUserMessage` 的 `deliverAs: "followUp"`），firstmate 只是可行性先例不是规格来源。

## 三十三、生产运行时返修：锁回收、Pi 探测与派发失败（2026-09-22）

**锁回收**：单独的 `mkdir .controller.lock` 不能保护「判死→删除→重建」整体。acquire/release 先用 Perl `Fcntl::flock` 对持续存在的项目 `qwbuddy/` 目录加独占锁，并清除该已加锁 FD 的 close-on-exec 标志，让实际执行回收/释放的 Bash 继承同一内核锁，覆盖完整临界区；即使 Perl 父进程被 SIGKILL，Bash 结束前其他获取者仍不能进入。目录删除重建不改变被锁 inode；最后一个持锁进程退出时内核释放互斥。Perl 或 flock 不可用即报错，不降级为无互斥回收。原有「只回收已死 owner、未知拒绝」不变。

**Pi 探测**：`turn_end` 的 `--block --max-ms 1` 与常规值守共用 exit 2 合同：摘要只注入一次、清故障计数并立即恢复常规 `--block`。0 继续闲置，124 恢复值守，其他退出码退避。

**派发失败**：保留 F2 的顺序，`state: running` 与 `scenarios-fp:` 在启动前写好并核验，完整 `dispatch:` 在投递前追加。记录该次追加的真实字节偏移；投递失败时核对本行内容，只原位把九字节前缀改成 `not-sent:`，再追加 `blocked:` 失败状态。账本不做整份快照覆盖或截断，其他工人并发追加的行保持原字节。`qwb-run.sh` 与 `qwb-lint.sh` 的场景块提取均把 `not-sent:` 视为运行记录终止行；即使验收场景是最后一节，也不改变原冻结指纹。只有本次新建的 tab 可关闭；显式 `--pane` 和复用工人的既有窗口不关闭。同名复用须有本票历史派发，并核对实际 worker、物理 cwd 和 workspace；任何查询未知均拒绝投递。本节取代 §三十一 E 对失败时“删除最后一行”和同名即复用的旧描述。

## 三十四、生产生命周期返修（2026-09-22）

Claude Stop hook 的 `.hook.lock` 接管和释放只在对项目 `qwbuddy/` 目录持内核 flock 的短临界区执行；值守本身不占该锁，以免挡住主控的正常锁操作。锁内复核活 PID，释放前复核本实例 token 与 PID；异常中断后的死 PID 由下次 hook 自动回收。

Pi 扩展在晚获主控锁后的 `turn_end` 启动一个值守；失锁、shutdown 和旧代际回调不得续命。子进程带宿主 PID，`--block` 写 `wake:` 前复核真实 PPID，宿主 SIGKILL 后不消费新进展。扩展等 stdout/stderr 排空后判退出码，按 PID 只清自己的 `.watch`。此机制只验证了本机 Bash/Node/`ps` 路径；真实 Pi reload 与跨平台宿主行为仍待设备验证。

可见 tab 的 `--ensure` 在任何副作用前解析项目目标 workspace，创建、扫描、登记、复用和失活恢复都使用该范围；主控 pane 仍核对为调用者 workspace 的指定目标。错误目标及查询未知时拒绝行动。
