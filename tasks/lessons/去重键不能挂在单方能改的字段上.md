# 去重键不能挂在「只有单方能改」的字段上

**日期**：2026-09-15
**发现者**：Astra medium 独立审核（F3，致命）；主控独立复现确认，根因是**主控自己的规格错误**

## 现象

QW buddy 的唤醒机制（`bin/qwb-wake.sh`）第一版用「任务书头部的 `state:` 字段」作为**未结项判定**与**去重键**：

```
未结项 = state ∈ {running, blocked, needs-decision}
不再叫 = 最近一条 wake 行的 state == 当前 state
```

后果：**第一次叫醒之后，工人干完活也永远不会再叫主控**。

因为 `state:` **只有主控能改**，工人只追加状态行。于是时间线是：

```
state: running
   ↓ 值守叫醒一次 → 写 wake: ... state=running
   ↓ 主控醒来看到「工人还在干活」→ 不改 state（没什么可改的）
   ↓ 工人完成 → 追加 done: 行 → 但 state 仍是 running
   ↓ 值守下一轮：state 未变 → 跳过 → 永久跳过
```

实测（主控独立复现）：

```
$ qwb-wake.sh --project $P --dry-run     # 账本：state: running + wake 行 + done: 行
跳过：2099-01-01-fake.md state=running（已叫过，状态未变）
```

`done:` 与 `blocked:` 两种行都被同样吞掉。**唤醒机制在正常完成路径上不成立**——而这是整个项目的命门（DESIGN §4.3 的第一需求就是「主控叫得醒」）。

## 根因

**去重键挂在了不会变的那一侧。**

判断「有没有新变化」时，键必须由**真正会产生变化的那一方**提供。这里：

| 谁 | 能改什么 |
|---|---|
| 工人 | 只能**追加状态行**（`working:` / `done:` / `blocked:` / `needs-decision:`） |
| 主控 | 能改 `state:` 字段 |

把键只挂在 `state:` 上 = 把唯一会频繁变化的信号（工人的状态行）丢掉。

## 对策

**指纹**必须包含会变的那一方：

```
fp = sha1( state 值 + "\n" + 最后一条 ^(working|done|blocked|needs-decision): 行原文，无则空串 )
叫醒后写：wake: <ISO时间> state=<值> fp=<sha1>
不再叫的条件：最近 wake 行的 fp == 当前 fp
```

要点：

- 指纹里**不含** `wake:` / `dispatch:` 行（运行时记录不能自己触发自己）。
- 旧格式（无 `fp=`）的 `wake:` 行必须视为「指纹不同」→ 允许再叫一次。**宁可多叫一次，不可漏叫**。
- 判断顺序永远是「漏叫的代价 > 多叫的代价」：多叫只是主控白跑一趟；漏叫是活停在账本上没人管。

## 教训

1. **设计检测/去重逻辑时，先问「这个字段谁会改」**。键必须来自会变的一方，或包含会变的一方。
2. 「同一项不重复叫」这种优化，天然有**漏报**风险，必须用真实时间线（工人完成后会怎样）推导，不能只看单轮输出。
3. 单轮测试全绿也会掩盖它——`--once` 跑一次看起来完全正常（叫醒了、wake 行也写了）。**流程类缺陷要用「状态转移」测，不是用单次调用测。**

## 这个坑的结构性原因

它是**规格错误**而非编码错误：实现严格照做了主控给出的规格。教训因此更深一层——**验收要验规格对不对，不只是验实现符不符合规格**。本轮是独立审核（换模型家族）读出了规格里的洞，主控自己的端到端门全部通过而毫无察觉。
