# 测试桩失效会打到真 Herdr

2026-10-03，全仓审核第 1 波。主控（Claude Code）并行派了五个 Pi 工人，各自在隔离副本里跑全门。

## 经过

1. 一个工人为清理临时文件执行了 `rm -rf <系统临时目录>/tmp.*`，把另一个工人正在跑的 `tests/smoke.sh` 的 `$TMP` 整个删掉。
2. smoke 的假 herdr 在 `$TMP/stubbin`，只靠 `PATH` 前置遮住真 herdr。桩没了之后，后续各节的 `herdr` 调用全部打到真服务。
3. 真 Herdr 里多出两个 Space（`wtproj`、`wtsetup`），另一个项目的主控 workspace 里多出 6 个 tab，每个都起了真 Pi 并收到测试夹具票的提示词。Rocky 发现后要求查清并禁止。主控按「cwd 位于该次 smoke 的临时目录」逐个核对后关闭。

## 教训

- **测试必须失效关闭**：隔离不能只靠「桩排在 PATH 前面」。连接目标（`HERDR_SOCKET_PATH` 等）要先指向死路径，桩不在时宁可失败。
- **任务书必须写明禁止通配删除**：只许删自己 `mktemp` 出的确切路径。「临时目录自己建自己删」这句话不够。
- **测试临时目录放在本项目内**（Rocky 2026-10-03）：不往系统目录、不往 Herdr 根层级或别的项目的 workspace 里开东西。
- 并行验收时出现与被验代码无关的「No such file or directory」，先查各工人会话记录里的 `rm`。

## 同日另一条纠正：排 pi 不要自己指定模型

Rocky 说「排 pi」，主控照 9 月 24 日的旧记忆给工人显式传了 `--model zai-coding-cn/glm-5.3-flash`，而 pi 当时的默认已是 magpie `codex/gpt-6.1-sol` high。Rocky 叫停并要求立刻切换。派工前先读 `~/.pi/agent/settings.json` 现查默认；模型以当轮指令为准，历史路由不是默认。

## 2026-10-04 真机验收抓到的缺陷

全仓审核收尾时，主控在全门全绿的 `main` 上跑 `tests/e2e-real.sh`，三轮里：

- 两轮没进入产品流程——验收脚本核对「主控界面显示的模型」的正则是照旧版 CLI 写的，认不出现在的 Codex（`GPT-6-Luna max · Context …`）与 Pi 状态栏（`🔌 magpie 🤖 codex/gpt-6.1-sol 🧠 high`）。
- 一轮（Claude Code 主控 + devin 工人）走完了派发、值守唤醒、验收、合入，最后 `finish --merged` 被拒：devin 运行时有两个同名前台进程，`activity()` 的「名字匹配恰好一个」认不出原生进程，派发证据里没有 PID，收尾要的死亡证明永远拿不出来，也没有任何合规的补救办法。

假 Herdr 的 844 条断言没有一条能发现这两件事。

教训：

- 假件只能证明「产品与假件一致」。CLI 界面、进程形态、Herdr 应答这些来自真环境的东西，只有真机验收能验。
- 真机验收脚本本身也会过期，要定期真跑；它跑不起来这件事本身就是一条发现。
- 收口前跑一轮真机验收，写清楚验的是哪一种主控与工人的组合，没验到的照实列出。
- 验收时只读地查真实形态（在独立的 named Herdr 会话里起一个空闲的工人，看 `pane process-info`），比猜快，也比猜准。

## 2026-10-04 真机演练抓到的第二批缺陷

**发生了什么**：收口前在独立 named Herdr 会话里演练 `--writer-proof-missing`，发现两件事。

1. 真 Herdr 0.9.3 对没有 agent 的 pane 根本不返回 `agent` 键；产品四处要求「键存在且为 null」，假 Herdr 夹具一律返回 `"agent": null`。测试全绿，真机上 pane 仍在的兑底收尾永远被拒。
2. 工人停在自己界面里时，默认 `finish --merged` 必然被「候选写入者仍持cwd/FD」拒绝，产品与说明都不写出路。当天 Claude Code 主控的真机验收断言全过，但读它的会话记录才看到：它被拒两次，自己读源码、让 devin 退出、把工人 shell 挪出副本才收尾。

**根因**：假桩的应答形态是照产品代码的期望写的，不是照真机抄的；验收只看断言结果，没看主控是怎么走到结果的。

**以后怎么做**：
- 写或改假 Herdr 夹具时，应答的键集合从真机 `herdr pane get` 等命令的实际输出抄（只读查询即可），「字段缺失」与「字段为 null」各测一遍。
- 真机验收通过后，读主控会话记录里所有被拒的命令和它之后的动作；主控靠翻源码才绕过去的地方，就是产品缺提示或缺文档的地方。
- 涉及删除判定的改动，收口前用独立 named 会话做一轮真机演练（脚本要点：`herdr --session 名 server` 起服务、`HERDR_SOCKET_PATH` 指过去、临时项目建在仓库 `.qwb-tmp/` 下、结束 `session stop` 加 `session delete`）。

## 2026-10-05 主控把没核实的字段写进返修指令

**经过**：`prompt-submit` 票第 1 轮返修，主控要求「投递前后比较 `state_change_seq`」，并写明「真 Herdr 的 `pane get` 与 `agent get` 都返回这个字段」。依据只是在 `agent start`、`agent prompt` 的应答里见过它，没有对 `pane get` 实跑。工人按指令用 `herdr pane get` 实现，假 Herdr 夹具也加上该字段，快门、定向测试与全门（858 PASS）全绿。主控验收时对照演练里保存的 `pane get` 真实应答，发现没有该字段，再实跑确认：`pane get` 的 `result.pane` 没有，`agent get` 的 `result.agent` 才有。按原实现真机上每次派发都会在状态校验处被拒。

**教训**：
- 任务书和返修指令里凡是写到「真机返回某字段」，先在真机上把那条命令跑一次，把应答存成样本文件，在指令里给路径，不凭印象写。
- 工人不许碰真 Herdr，所以真实应答的形状只能由主控提供；主控写错，假桩就跟着错，测试全绿也拦不住。
- 验收涉及 Herdr 应答形状的改动时，把实现里读的每个字段同真实样本逐个对一遍。

**同日再犯**：`reuse-binding` 票里主控又写了两句没核实的话——「Herdr 在 `agent start` 返回时就已经给出 `agent_session`」和「脚本在会话文件未落盘时丢掉了 session」。前一句的依据是 `agent prompt` 的应答与事后的 `pane get`，不是 `agent start` 的应答；后一句没读 `bin/qwb-herdr.sh` 第 173–174 行就下了结论。工人读代码后用离线探针推翻并写了 `needs-decision:`，没有照错指令实现。主控随后在隔离会话实测：`agent start` 的应答没有 `agent_session`，约 1.5 秒后 `pane get` 才报出。这次没造成返工，是因为任务书里留了一句「推断不成立就写 `needs-decision:`」。

- 「某条命令的应答里有某字段」这句话只对实跑过的那条命令成立，不能从别的命令的应答推过去；时序相关的事实还要写明是在哪个时刻观测的。
- 任务书里的根因凡是主控的推断，一律标明是推断并给工人留出反驳的出路；这条这次起了作用，以后照做。
