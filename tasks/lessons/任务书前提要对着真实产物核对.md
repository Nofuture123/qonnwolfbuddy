# 任务书前提要对着真实产物核对

2026-10-05 一天之内，主控五次把没核实的东西当事实写进任务书：

- `reuse-binding`：写「脚本丢了会话」「`agent start` 返回里已有会话」，都不成立；
- `collab-silence-fallback`：范围自相矛盾；
- `land-env-digest`：写「落地四步都比对环境」，实际三步；
- `roles-polish-code`：照抄演练主控的记录「主控自己的授权行成了主控待办」，代码里它是给规划的；
- `claude-role-adapter`：只看了 `templates/workers.sh` 就写「Claude 工人参数只允许三种」，没看安装器实际写进项目的声明带 `--add-dir`（而本目录早有一条教训专门记了这件事）。前四次被工人对照代码推翻，这一次工人照做了，离线测试用的是手写声明，全门通过，直到真机演练第一步才被拒。

教训：

- 写「某文件里是什么」「某命令返回什么」之前，对着**真实产物**看一眼：安装后的项目文件、真机响应、实际运行的输出。模板不等于安装后的样子。
- 给不出实测出处的前提，在任务书里标成推断，并写明「与代码或实测不符就写 needs-decision」。前四次没酿成错误实现，全靠这一句。
- 新功能的离线测试要用安装器真实装出来的配置，不用手写的理想配置。
- 开工前先翻 `tasks/lessons/`，同一个坑不踩第二遍。
