# 定级与放行前跑通真实链路

2026-09-24 生产优化审核中，主控三次先下结论，后来被实测推翻：

- 没对照计划第 6 条（最终 SHA 必须有真实闭环），就说「可以合并」。
- 唤醒摘要截断的严重度改了两次口。第一次没测 Herdr 会不会拒收，就定为 LOW；第二次没查三种宿主实际走哪条投递路径，就改为 HIGH。实测之后才定为 MEDIUM。
- 分析工人重名时，拿完整文件名推演，没读 `qwb-run.sh` 实际怎样得出任务 id（它会去掉日期前缀）。结果机制和数字都写错了，r4 审核报告只能追加更正。

以后照这三条做：

- **定级前**：把后果链路实测到使用者能看到的终点，比如真 Herdr 的投递、各宿主的正式入口。只看到中间现象时，直接说「影响未核实」，不给级别。
- **推演前**：先读产生输入的那行代码，再用真实数据跑一遍，然后才写数字。
- **放行前**：说「可以合并」或「可以收尾」之前，对照计划里的交付条款逐条打勾。

**2026-09-24 三主控 E2E r2 又犯一次**

- 审核者在 r2 任务书里推荐「pi 扩展 exit 2 投递后，等下一次 `turn_end` 再重启值守」，事先没有读 pi 本机文档。
- 实际上，`turn_end` 在每次模型请求后都会触发，一次忙碌运行里会出现很多次（见 `docs/extensions.md` 第 109 行）；followUp 要等整次运行结束才送达（见 `docs/sdk.md` 第 68 行）。
- 执行者照推荐实现后单元测试全过，真机却失败了：10 条唤醒里有 9 条在收尾后才送达。执行者改用 `agent_settled` 之后才过。

**补一条规则**

- 任务书里推荐某个宿主事件或 API 的用法之前，先读该宿主的本机文档，确认它的语义和触发频率，并写明依据的是文档哪一行。
- 没核实就写「待执行者实测确认」，不要写成推荐做法。
