# 咨询任务书：如何让系统识别「票本身就有问题」

```
咨询 id:   qwbuddy-ticket-defect-consult
state:     running
顾问:      gpt-6-astra / **high**（Codex CLI）
产出:      docs/reviews/2026-09-15-票缺陷识别-咨询.md（本轮唯一允许写入的文件）
你的身份:  **咨询师**（不是审核者）—— 你要**给判断、给建议、给取舍**，可以提方案。
```

---

## 一、项目目标（判断一切取舍的尺子，三句话）

QW buddy 是**装进单个项目**的「AI 主控协作层」：一份说明书 + 8 个 shell 脚本（约 1100 行）+ markdown 账本。它管的不是"一个 AI 怎么把活干好"，而是**「活本身怎么被派发、验证、记住」**：主控写任务书（票）→ 派给 Herdr 窗口里的工人 → 值守把主控叫回来 → 主控独立验收 → 记账。

三条尺子：① 谁的状态归谁；② **薄即抗淘汰**（只持有跨模型厂商调度 + 项目账本与验收纪律）；③ 能自动检查的规范不要只写在纸上。
硬边界：零通知使用者、无队列/ACK/数据库/守护进程、只用 Herdr、纯 shell 零外部依赖、不动架构。

## 二、要解决的问题（使用者提出）

> 「我们让主控或者第二个主控去开票的时候，可能会出现票开得有问题的情况。执行者审核了一遍、两遍、三遍，到第三遍审核出来发现依然有问题时，**系统并不会自动去识别是不是票本身的指令有问题**。这种情况下，我们该如何升级，把这个问题解决掉？」

**本项目里已经真实发生三次**（都能查到）：

| 事件 | 票里怎么写的 | 真实根因 |
|---|---|---|
| F3「唤醒闭环在正常路径上不成立」 | 主控在票里把「未结项」与「去重键」都挂在 `state:` 字段上 | **主控的规格错**：`state:` 只有主控能改，工人的完成信号永远触发不了第二次叫醒。票里白纸黑字写着「根因是主控的规格错误」 |
| M1「先场景后代码没有执行门」 | 主控在票里要求"先场景后代码" | **主控预判过这个疑虑却没落成机制**，只有关键词断言 |
| R2-M4「负例断言是假的」 | 主控在票里要求"补负例断言" | **主控的要求本身有洞** —— 没说断言必须能失败 |

三次都是「执行者忠实照做、做对了，但规格不对」，而**系统每次都把返修当成"实现问题"继续派下去**。

## 三、现状调查（已做，你可以直接采信，不必重复；需要时可抽查）

- `grep -rn 'rework|返修计数|spec-suspect' bin/ templates/ tests/` → **零命中**：完全没有"返修计数/规格怀疑"概念。
- **验货门**（`templates/QWBUDDY.md` §5）只有 4 条：不采信工人自述 / 留痕 / 通过→`verified`、不通过→返工或记错题 / 主控可自干小活。**没有一条是"怀疑票本身"**。
- **状态行**只有 4 个：`working:` / `done:` / `blocked:` / `needs-decision:`。工人**没有"这张票本身有问题"的通道**（`needs-decision:` 语义是"需要你选个方案"）。
- **任务书头部字段**（`templates/TASK.md`）：任务 id / state / 来源 / 派发 / 主账本 / 工作目录 / 分支。**没有返修计数、没有根因归类**。
- **场景冻结**：`scenarios-fp:`（sha1）+ `--accept-new-scenarios`（丢基线时显式重建）。**只有"冻结"和"重建"，没有"显式修订并留痕"的通道** —— 改场景目前一律 lint FAIL。
- 返修历史只存在于**主控手写的验收记录散文**里，没有任何脚本读它；**换主控后没人会因为这行字改变行为**。

## 四、初步方案（主控拟的，请你判断——不是让你照做）

| 层 | 内容 | 拟投入 |
|---|---|---|
| **0** | 新增状态行 `spec-defect: <票里哪条有问题、为什么>`：工人一发现就写，不必等到第三遍；主控验收**必须先处理它**（改票或明确说明为何不是票的问题），不许直接再派一遍实现 | 规范 + ~5 行脚本 |
| **1** | 票头加 `rework-count:` 与 `rework-causes:`（`impl` / `spec` / `doc` / `gate` 四类计数）；验收不通过时**每条返修项必须归类**；lint 检查自洽 | ~20 行 + 模板字段 |
| **2** | `qwb-run.sh` 自动识别：`rework-count ≥ 2` **或**票上有 `spec-defect:` → **拒绝按原票再派实现**，提示先走"审票" | ~30 行 |
| **3** | 审票流程：换模型家族，按四个审点审「票本身」（票内部自洽 / 与上游文档承诺一致 / 场景与失败路径够不够 / 验收门是否"可失败"） | 复用现有审核机制 + 一组审点 |
| **4** | 改票的合法通道 `qwb-run.sh --revise-scenarios=<原因>`：写 `scenarios-revised:` 留痕并重算指纹；lint 对"无痕改场景"仍 FAIL（区分"偷改"与"显式改票"） | ~15 行 |
| **5** | `spec` 类返修强制进错题本（专节「票的规格错」）；主控开局点名列 `rework-count ≥ 2` 的票并优先处理（顺带解决"换主控后看不见历史"） | 规范为主 |

## 五、请你回答的六个问题（这是本轮的核心）

请**逐条回答**，并给理由。允许你说"这一层不要做"。

1. **逐层判断**：0–5 层里，哪些是「必须补」，哪些是「可以不要」，哪些应该**合并或砍掉**？请给出你建议的最终形态（可以是 0 层、1 层，也可以是别的组合）。
2. **触发条件**：`rework-count ≥ 2` 合适吗？**每多触发一次"审票"就是一轮额外 token 成本**（这个项目已经跑了六轮对抗审核）。你会怎么设计触发条件，让它既早发现、又不滥用？
3. **归类口径**：`impl` / `spec` / `doc` / `gate` 四分法够用吗？能否更简（例如只分"实现的错"与"上游的错"两类）？归类由**主控手工标**是否可接受，还是必须机器可判？
4. **有没有更薄的做法**：解决同一个问题，是否存在**比上面五层更少机制**的方案？（例如只做第 0 层、或只做一个字段、或完全靠规范不写脚本）如果有，请写出它，并说明它的失效边界。
5. **反向风险**：这个机制会不会被滥用或反噬？例如：工人**滥用 `spec-defect:` 给自己甩锅**；或者"票一被怀疑就停下审票"导致**本可一轮修好的事被拖成两轮**。你建议怎么防？
6. **成本效率的平衡**：使用者的原话是「不过度设计，不浪费不必要的 token，保持成本效率的平衡」。请针对你建议的最终形态，给出**成本估算**（脚本行数 / 每票新增的人工或 token 开销 / 触发频率的直觉估计），并说明**为什么这个投入值**。

## 六、约束与产出要求

- **不要过度设计**：不引入守护进程、数据库、新依赖、新服务；不改"账本 + 脚本 + 换模型家族审核"这个形态。
- **建议必须可落地**：给出具体落点（改哪个文件、什么字段名、什么条件），不要停留在原则层。
- **简洁优先**：你的产出请**先给结论表**（每层：做 / 不做 / 简化 → 一句话理由），再给必要论证；**不要复述任务书背景**。任务书已给的调查结果不必重述。
- 你**可以**抽查代码/文档确认，但**不要**做大范围重读（背景已给全）。
- 除产出文件外**只读**。
- 产出写 `docs/reviews/2026-09-15-票缺陷识别-咨询.md`，最后一行打印 `CONSULT DONE <建议做的层数>/<建议砍掉的层数>`。
