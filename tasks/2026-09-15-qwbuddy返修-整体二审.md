# 批 1：两条致命

## F1（致命）：工人无终态行时，主控永远不被叫醒

**事实（主控已复现）**：任务书含 `state: running` + `working:` + 一条已叫过的 `wake:` 行；工人随后挂起/崩溃、**没有追加任何行**。指纹只含 `state` + 最后一条状态行，于是**每轮都「跳过…进展未变」**，存活且空闲的主控**永远不会再被叫醒**——违反 `DESIGN.md` §4.3「工人退出 ≠ 完成：退出但账本里没有结论的，仍算未结项」。

**规格**：

1. `templates/config.sh` 新增：

```sh
QWB_REWAKE_MS=1800000                  # 时间兜底重叫：距上次叫醒超过它仍未结项就再叫一次（0 = 关闭）
```

2. `qwb-wake.sh` 的「是否需要叫醒」判断改为：

- **指纹变了** → 叫（现有行为，保持）
- **指纹未变**，但最近一条 `wake:` 行的**时间戳**距现在 ≥ `QWB_REWAKE_MS`（且 `QWB_REWAKE_MS > 0`）→ **也再叫一次**（这就是「兜底重叫」：工人挂起/崩溃时把超时判断交回主控），并照常追加新的 `wake:` 行。
- `--dry-run` 下同样要执行这个判断（输出「未结项（将叫醒）」），但**不写** `wake:` 行。

3. 时间戳解析：现有 `wake:` 行格式是 `wake: <ISO8601 UTC> state=<值> fp=<sha1>`。用**纯 shell** 解析（`date -u -j -f` 在 BSD/ macOS 可用，或用 `perl -MTime::Piece`——二者都在允许范围内）。**解析失败时**：保守处理为「视为超期 → 叫醒」（宁可多叫，不可漏叫），并把该判断写进注释。

## F2（致命）：派发时整体覆盖任务书，会抹掉工人并发追加的结果

**事实（主控已确认）**：`qwb-run.sh:131,135` 先 `awk` 把任务书读成快照改 state，再 `mv` 整体覆盖。而脚本**在此之前就已经启动工人并发了提示词**，工人被允许往同一份任务书追加。若追加发生在「快照读完之后、`mv` 之前」，追加行被旧快照吃掉，派发仍退出 0 宣告成功。

**规格**：

1. **顺序调整**：把「改 `state:` + 追加 `dispatch:` 行」**移到启动工人之前**。推荐顺序：
   ```
   定位任务书 → 校验（含 M1 的场景门）→ 改 state / 写 dispatch → 开窗（tab create）→ agent start → agent prompt
   ```
   注意 `dispatch:` 行要记 pane id，所以「开窗拿到 pane id」可以在「写 dispatch」之前，但**`agent start` / `agent prompt`（工人开始能干活的时刻）必须在所有对任务书的写入之后**。
2. **改 state 不得整文件覆盖**：只替换 `state:` **那一行**，其余行**原样保留**（例如 `awk` 只改匹配行、输出到临时文件后 `mv`——**前提是这发生在工人启动之前**；或直接原地逐行替换）。**禁止**"先读整份快照、过一会儿再覆盖"的模式。
3. **可验证性**：写完后自检——任务书里**原有的所有行仍然存在**（行数只增不减）。
4. `tests/smoke.sh` 增加**负例断言**：用 `awk` 函数替身注入一个「在改 state 的瞬间工人追加了一行」的时点，断言这行**没有丢**（参考审核报告 F2 的复现手法）。若你的实现让这个注入无法产生丢失，断言通过；**若实现改法让注入点不存在了，也要断言"派发后工人追加的行在文件里"**。

# 批 3：三处整装断点（都要负例）

## M1（必须补）：任务书的「先场景后代码」只有模板与关键词，没有执行门

**事实**：`qwb-run.sh` 只定位任务文件、**不要求场景**；lint 四项也没有这项；smoke 只 grep 模板里有没有 Given/When/Then 这些**词**。用户明确指出过这个疑虑（"场景冻结有没有可强制的手段"），上一轮却没落成机制。

**规格**：

1. **派发门**：`qwb-run.sh` 在派发前检查任务书：
   - 必须含「验收场景」块（识别 `Given` + `When` + `Then` 三个关键词各至少出现一次，或 ≥2 个 `### user_...` 场景标题）；
   - **至少一条失败路径场景**（该场景的标题或 `Then` 段里出现"失败/拒绝/报错/异常/负例/非法/fail/error"等标记之一）；
   - **不满足 → 拒绝派发**（退出码非 0，并打印"请按 `qwbuddy/TASK.md` 补验收场景（至少一条失败路径）"）。
2. **冻结可验证**：派发时计算「验收场景块内容」的 sha1，写入任务书一行：`scenarios-fp: <sha1>`（写在 state 附近）。`qwb-lint.sh` 增加检查：重算当前场景块指纹，与 `scenarios-fp` 不一致 → **FAIL**，并提示"验收场景在派发后被改动"。
3. **lint 同步**：`qwb-lint.sh` 也检查场景存在性与失败路径（对已派发/已结项的任务书）。
4. **负例断言**：
   - 空场景任务书 → `qwb-run.sh` **拒绝**（现有 smoke 里那个"无场景也派发成功"的断言要改）；
   - 派发后改动场景块 → `qwb-lint.sh` **FAIL**。
