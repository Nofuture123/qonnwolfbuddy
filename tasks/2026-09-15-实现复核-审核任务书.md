## 三个审点（已返修 —— 本轮复核修复是否正确）

### 审点 1：worktree 收尾——「有规范、无实现」

**已核实的事实**：

- `templates/QWBUDDY.md` §6 写了完整四步规范（开 / 收·成功 / 收·废弃打 `archive/<任务id>` 标签 / 留·例外），并注明「谁派生谁收尾」「`git worktree prune` 清元数据残留」。
- 但 `bin/` 里**没有任何 worktree 收尾实现**：无 `git worktree remove`、无 `git tag archive/...`、无 `git worktree prune`。规范只存在于说明书，执行靠主控手动。
- 且 §6 第一步要求「开之前**先清点**——有已完成任务的残留就先收掉」，而 `qwb-run.sh --create-worktree` 只有 `mkdir -p` + `git worktree add`，**没有清点动作**。

**请审**：这是「必须补」（不收尾会导致 worktree 与分支堆积——正是设计要防的失败模式），还是「可以不要」（主控手动执行说明书即可）？
若属必须补：最小实现是什么、应落在哪个脚本的哪一步（派发前清点？新增收尾脚本？），以及会不会因此引入新的状态需要记账。

### 审点 2：并发工人时的唤醒延迟 + 一处死配置

**已核实的事实**：

- `qwb-wake.sh` 的 `wait_round` 只取未结项任务书中**时间戳最新的一条** `dispatch:` 行，做**一次** `herdr agent wait`。
- 因此两个工人并行时，另一个工人的完成**只能等本轮等待结束、循环回头扫账本时才被发现**，最大延迟 = `wake_interval_ms`（默认 120000 毫秒 = 2 分钟）。
- 另核实：`templates/config.json` 的 `timeouts.agent_wait_ms`（1800000）**未被任何脚本读取**（死配置）；实际等待上限取的是 `wake_interval_ms`。

**请审**：这个延迟在 MVP 下可接受吗？若可接受，是否应写进 `DESIGN.md` 的已知限制（而不是留在代码里靠人读出来）？那处死配置应当删除还是接上？

### 审点 3：配置读取是「用正则猜 JSON」，两处静默风险

**已核实的事实**：

- `qwb-run.sh` 与 `qwb-wake.sh` 用 `sed` 正则抽取 `wake_interval_ms` / `pane_id` / `agent_start_ms`，且都以 `| head -1` 收尾——**同名字段出现多次时静默取第一条**。
- 工人名校验是 `grep -q "\"$WORKER\"" "$CONF"`——**整文件子串匹配**，工人名出现在任意字符串里（说明文字、routing 文案、note）都会被判为「该工人在工人表里」。
- 两处都是**静默错误**（不报错、不落痕），与本项目自己定的「失败必须留痕 / 不静默」原则相冲突。

**请审**：这算「必须补」还是「可以不要」？若补，最小方案是「配置保持扁平 + 读取后显式校验」，还是引入 `jq`（**代价：多一个依赖**，与项目零依赖的现状冲突）？
