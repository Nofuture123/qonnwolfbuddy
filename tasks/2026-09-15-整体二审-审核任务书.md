## 一、项目目标（审核前必读——这是你判断一切设计取舍的尺子）

**QW buddy 是什么**：一个**装进单个项目**的「AI 主控协作层」，形态是 **一份说明书 + 几个 shell 脚本 + markdown 账本**。它**不是应用软件、不是独立程序、不是守护进程**。

**它解决三个真实问题**（使用者在项目里用 Claude Code / Codex / Pi 干活时遇到的）：

1. **主控会「叫不醒」**——任务派出去、工人干完了，主控回合结束就不再回来验收，流程断掉。
2. **没有身份切换**——同一个会话无法在「主控 / 审核者 / 执行者 / 咨询师」之间规范切换。
3. **没有派工标准**——什么活发给哪个模型（不同 CLI、不同能力、不同额度）没有明确判据。

**使用者的角色只有一件事：提需求。** 验收、落地、超时判断全部下放给主控（主控是强模型，判断力优于使用者本人）。但**权力下放必须可审计**：主控要把「跑了什么检查、结果、结论」写进账本留痕。

**设计哲学（三条尺子，用来判断任何取舍）**：

- **谁的状态归谁**：状态属于产品（会话/模型/厂商）→ 交给那个产品；属于使用者与项目（任务/验收/教训）→ 放在产品外面，也就是这一层。
- **薄即抗淘汰**：Harness 会越来越强，会吃掉「等待、通知、记忆」；QW buddy 只持有它吃不掉的——**跨厂商调度 + 属于项目的账本与验收纪律**。
- **能自动检查的规范不要只写在纸上**：写在说明书里靠人记得的规范，等于没有（本项目已被坑过两次，见 `docs/DECISIONS.md` §21）。

**明确的硬边界（有意不做，不要当成缺陷）**：

- **零通知使用者**（唯一「叫人」动作是 `herdr` 叫醒主控窗口；钉钉/桌面通知/弹窗一律不做）
- 无队列 / 无 ACK 协议 / 无数据库 / 无守护进程 / 无 cron
- 只用 Herdr（不用 tmux / zellij / orca / cmux）
- 工人一律在 Herdr 窗口**交互式**运行，**禁 headless**
- **不自动拉起已退出的主控**（主控死了由使用者重启，从账本续接——这是明确的 MVP 边界，见 `DESIGN.md` §10）

**当前状态**：MVP 已实现并验收；此后经历**四轮对抗性审核**（2 致命 + 4 必须补 + 2 可以不要，全部修复）与一轮**测试纪律吸收**。所有轮次的报告在 `docs/reviews/`，决策记录在 `docs/DECISIONS.md`（已到 §21）。

## 四、期望你回答的验收场景（本项目刚确立的规范：先场景后代码；此处示范用于审核）

请对每条给出明确结论 + 证据（通过 / 不通过 / 部分）：

### user_目标与实现自洽
- **Given** 项目目标声明了三件事（叫醒主控 / 身份切换 / 派工标准）与若干硬边界（零通知、无队列、只用 Herdr 等）
- **When** 逐条比对 `DESIGN.md` / `QWBUDDY.md` 的承诺与 `bin/` 的实际实现
- **Then** 每条承诺都能指出**具体的实现位置**；不存在「承诺了但没有任何实现」的条目；也不存在**违反硬边界**的实现

### user_装进真实项目不缺件
- **Given** 一个空白项目
- **When** 走完 `qwb-init.sh` → 主控开局点名 → 派活 → 工人在窗口干活 → 值守叫醒 → 主控验收 → worktree 收尾 这条链
- **Then** 每一步都有对应的脚本或明确的说明书步骤，**没有断点**；文档提到的每个文件/命令都真实存在

### user_规范不是纸面的
- **Given** 项目刚吸收的五条测试纪律（先场景后代码、禁无契约 fake、E2E 与分级、失败路径优先、规则写成 lint）
- **When** 逐条检查它们在仓库里的落点
- **Then** 每条都能指出**可执行的落点**（脚本、模板、lint 检查、fixture），而不是只出现在某段说明文字里；并且这些落点**真的会产生效果**（例如 lint 能发现违规、fixture 能挡住契约变化）

### user_失败路径被认真对待
- **Given** 前四轮审核抓到的几乎全是失败路径/异常场景（detached HEAD、投递失败、并发推进、非法 state、跨段误读）
- **When** 看现在的测试与实现
- **Then** 你能指出测试里**覆盖了哪些失败路径**、以及**仍然没有覆盖的关键失败路径**（后者才是重点）

## 五、三个审点（严格限于此三点，不要扩大）

### 审点 1：目标与实现的自洽性
上面 `user_目标与实现自洽` 场景。重点找：**承诺了但没有实现**的（本项目历史上已出现过两次）、**实现违反了自己定的边界**的、**文档之间互相矛盾**的。

### 审点 2：测试纪律是机制还是说法
上面 `user_规范不是纸面的` + `user_失败路径被认真对待`。特别检查：

- 「先场景后代码、场景冻结」有没有**任何可强制的手段**？还是只是一句写给 AI 看的礼貌要求？（若只是文字，这本身就是一个发现——它与本项目"能自动检查的规范不要只写在纸上"的哲学冲突）
- `qwb-lint.sh` 的四项检查**能被绕过吗**（本项目刚发生过 `"config.jso""n"` 字符串拼接躲门的事件，见 `DECISIONS.md` §19）？
- `tests/fixtures/herdr/` 的契约断言**真的能挡住 herdr 输出形状变化**吗？
- 快门/全门的分级是否**真的省时间**（给出你自己的测量）。

### 审点 3：整装的可用性与一致性
上面 `user_装进真实项目不缺件`。重点找：装进一个**真实的、不是本仓的**项目时会不会缺件、路径假设是否成立（例如 `qwb-init.sh` 从何运行、`qwb-test.sh` 的 config 回退逻辑、`qwb-wake.sh` 对 config 的依赖）、说明书里的步骤顺序是否可执行。

- **只挑错**，不提方案、不写实现、不改代码；区分「必须补」与「可以不要」，**不要凑数**。
- 证据具体到文件与行号，或给出可复核的最小复现（内存替身可以，但**必须标明是替身**；能真跑就真跑）。
