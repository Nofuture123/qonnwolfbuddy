## 一、项目目标（判断一切设计取舍的尺子）

**QW buddy 是什么**：一个**装进单个项目**的「AI 主控协作层」，形态是**一份说明书 + 几个 shell 脚本 + markdown 账本**。不是应用软件、不是独立程序、不是守护进程。

**它解决三个真实问题**：① 主控会「叫不醒」（任务派出去、工人干完，主控回合结束就不再回来验收）；② 没有身份切换（主控/审核者/执行者/咨询师）；③ 没有派工标准（什么活发给哪个模型）。

**使用者只做一件事：提需求。** 验收、落地、超时判断全部下放给主控（强模型），但**权力下放必须可审计**——主控要把「跑了什么检查、结果、结论」写进账本留痕。

**三条设计尺子**：① 谁的状态归谁（产品的状态交给产品，项目的状态留在项目外）；② 薄即抗淘汰（只持有跨厂商调度 + 项目账本与验收纪律）；③ **能自动检查的规范不要只写在纸上**。

**硬边界（有意不做）**：零通知使用者；无队列/ACK/数据库/守护进程/cron；只用 Herdr；工人一律交互式（禁 headless）；不自动拉起已退出的主控（MVP 边界）。

## 三、本轮目标（严格限于三点）

### 审点 1：八条修复是否真的成立

逐条独立复核 F1 / F2 / M1 / M2 / M3 / M4 / M5 / M6 的修复。**不要采信修复方断言、不要只重跑全门**——自己构造反例。尤其：

- **F1 时间兜底**：指纹未变但 `wake:` 超期时会再叫；会不会**反过来**造成"每轮都叫"（退化成打扰）？解析失败保守叫醒是否会让坏输入导致刷屏？
- **F2 记账顺序**：写 state/dispatch 移到 `agent start` 之前后，**还有没有别的窗口**能让工人追加丢失（例如 `agent start` 之后、`agent prompt` 之前工人就已经在写）？
- **M2 契约校验**：新的 `perl -MJSON::PP` 点路径校验**能不能被绕过**（例如 fixture 里字段存在但类型错误、值为 null、路径存在却在错误对象上）？
- **M5 门未声明**：报错非 0 会不会让**正常项目**（已声明门）受影响？`qwb-lint.sh` 的"门已声明"检查在母本仓自用场景（只有根 `qwb.config.sh`）下是否误报？

### 审点 2：「每道门都要有负例断言」这条硬要求，是否真的落地了

这是上一轮教训的直接产物。请检查：

- 每一条新门（场景门、契约校验、lint 补漏、快门逐文件、整装门、默认隔离）**是否都配了负例断言**？
- 这些负例断言**本身是否可靠**（例如：负例断言用的替身是不是又变成了"没有契约校验的假替身"？负例的期望值是不是恰好在错误实现下也会通过？）
- **有没有"负例断言是假的"的情况**——即把实现改回错误版本后，该负例断言**仍然通过**？请至少挑 2–3 条做这个"反转验证"（把实现临时改坏 → 断言应变红）。这是本轮最有价值的一项检查。

### 审点 3：整装可用性（第 2 轮）

- 从 `qwb-init.sh` 装进一个**真实空白项目**后，默认门、lint、派发、值守、收尾是否都给出**可理解的行为**（不是 127、不是假绿、不是静默跳过）？
- 母本仓自用场景（只有根 `qwb.config.sh`、没有 `qwbuddy/` 目录）是否仍然自洽？
- 说明书里的步骤顺序是否可执行（尤其：新项目装好后，**第一次该怎么声明自己的门**；`TASK.md` 场景块的写法是否清晰到能让一个 AI 工人照做）？
